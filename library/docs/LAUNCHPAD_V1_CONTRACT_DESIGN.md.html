표기 규약 - 불변: 배포 후 아무도 바꿀 수 없음(immutable/constant). 런처 선택: 토큰 생성 시 런처가 한 번 정하고 이후 불변. 타임락: 3일 지연 후 변경 가능한 유일한 상태. - 금액 단위는 ETH(1e18 wei), 토큰은 18 decimals. 1. 한 장 요약

무엇인가. 런처가 토큰 이름·심볼·salt·(선택) 데브바이·(선택) 크리에이터세·커브 티어를 정해 createToken을 호출하면, 같은 트랜잭션에서 (1) 토큰이 CreateX CREATE3로 두 체인 동일 주소에 만들어지고 전량 1e9가 커브 싱글턴에 민팅되며, (2) 수수료 원장(FeeEscrow)에 크리에이터 수취인이 등록되고, (3) 커브가 열리며 스나이퍼세 면제인 유일한 매수(데브바이, ≤5 %)가 실행된다. 이후 누구나 커브에서 사고판다(ETH 레그 1 % 수수료, 초반 5초 스나이퍼세). 판매 가능 물량 71.43 %가 소진되는 매수(크로싱 매수)가 같은 트랜잭션에서 졸업을 실행한다: 모은 ETH(Q)와 남은 토큰 20.41 %가 커브 마지막 가격 그대로 영구 풀에 들어가고(Robinhood: Uniswap v4 fee-0 풀 + MemeHook, GIWA: 자체 LaunchPair), 포지션은 인출 경로가 없는 PermanentLocker가 영원히 보유한다. 풀에서도 1 %가 quote로 징수되어 같은 에스크로에 80/20으로 쌓이고, 수취인이 pull-claim 한다. 배포 후 존재하는 권한은 "수취인이 자기 몫을 claim 한다"와 "크리에이터 수취인이 3일 타임락으로 지갑을 바꾼다" 둘뿐이다.

3. 컴포넌트별 사양

각 소절은 책임 → 스토리지 → 함수 → 이벤트/에러 → 불변식 순서다. 함수 시그니처는 interfaces/I*.sol이 정본이며 여기서는 의미만 적는다.

3.1 LaunchToken (ILaunchToken.sol)

책임. 고정 공급 밈코인. OZ ERC20 + ERC20Burnable. 소유자·민트·일시정지·블랙리스트·전송 훅·FoT 없음. ERC20Permit 없음 — OZ EIP712가 _hashedName 등을 immutable로 인라인하여 런칭마다 런타임 바이트코드가 달라진다(https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/contracts/utils/cryptography/EIP712.sol). Permit2가 두 체인 모두 canonical(0x000000000022D473030F116dDEE9F6B43aC78BA3).

스토리지. OZ ERC20 표준(_balances, _allowances, _totalSupply, _name, _symbol) + address launchpad(저장, 커브 주소). immutable 0개 → 모든 런칭·모든 체인에서 런타임 코드 동일 → Blockscout verified_twin 자동 검증.

주소. 팩토리가 CreateX deployCreate3(salt, creationCode ‖ abi.encode(name, symbol, CURVE)). 3.4 SnipeSchedule (공용 순수 라이브러리)

커브·훅·페어가 같은 함수를 링크한다. 체인·장소별 상수 분기 없음.

library SnipeSchedule {
    uint16 internal constant START_BPS = 9_900;
    uint8  internal constant WINDOW_SECONDS = 5;
    /// t = block.timestamp - anchor (정수 초). 표: [9900, 9900, 2475, 309, 38], t >= 5 -> 0.
    /// t >= 1 구간은 9900 >> floor(14 * (t - 1) / 5) 와 같다 (Pons 검증 소스 currentSnipeTaxBps의 14-halving 형태를 1초 뒤로 앵커).
    function snipeBps(uint256 t) internal pure returns (uint256) {
        if (t &lt; 2) return 9_900;
        if (t == 2) return 2_475;
        if (t == 3) return 309;
        if (t == 4) return 38;
        return 0;
    }
    /// 총 bps가 maxTotal(9900)을 넘지 않도록 잘라 매수자가 항상 >= 1 %를 받게 한다.
    function capped(uint256 snipe, uint256 otherBps, uint256 maxTotal) internal pure returns (uint256) {
        return otherBps + snipe > maxTotal ? maxTotal - otherBps : snipe;
    }
}

앵커: 커브 = launchedAt(open()의 block.timestamp), 풀 = initTimestamp(훅 beforeInitialize / 페어 mint의 block.timestamp). 매수에만 적용, 매도는 절대 아님. 수익은 100 % 프로토콜(protocolOnly 레그).

왜 이 모양인가(A1-03·A1-08·A2 §4를 합친 결론): Robinhood 타임스탬프는 초 단위이고(10블록/초 실측), ArbSys.arbBlockNumber() 보간은 벽시계가 아니라 트랜잭션 부하 시계라 런칭 순간(봇 스팸) 정확히 그때 세금이 더 빨리 줄고, 런처가 자기 트랜잭션을 뿌려 시계를 돌릴 수 있다(A1-08). 보간 없이 1초 표만 쓰면 "런칭 초 .8에 쏘고 다음 초에 두 번째 지갑으로 산다"가 6 %에 가능하다(A1-03). 그래서 t=0과 t=1을 모두 99 %로 앵커한다: 인간은 1초 안에 반응하지 못하므로 비용이 없고, 런처의 타이밍 트릭은 무력해진다. 이후 값은 Pons가 문서화한 T=5 스케줄(≈25 %, ≈3 %)이다. GIWA(1초 블록, 우선수수료 정렬)에서는 런칭 블록 t=0, 다음 블록 t=1(둘 다 99 %), 그다음 24.75 %.

UI 정량 문구(A1-03 (a)): "공개 데브바이를 제외한 런칭 후 2초 이내의 모든 매수는 99 % 세금을 냅니다. 3초째 24.75 %, 4초째 3.09 %, 5초째 0.38 %, 그 후 0 %. 세금은 전액 프로토콜로 가며 크리에이터에게 돌아가지 않습니다. 면제 지갑 목록은 존재하지 않습니다." — "번들이 구조적으로 불가능하다"고 쓰지 않는다.

3.5 MemeHook (Robinhood, IMemeHook.sol)

책임. 졸업한 모든 v4 풀에 붙는 싱글턴 훅. (a) 1 % quote 징수 → 에스크로, (b) 졸업 후 5초 매수 스나이퍼세, (c) initialize 게이트(TARGET만, 등록된 키만, 한 번만), (d) 잠긴 포지션 감소 거부(방어 심층). 소유자·setter·rescue 없음. 수취인은 훅에 없다(에스크로).

권한 비트(주소 하위 14비트) = 0x22CC. BEFORE_INITIALIZE 1&lt;&lt;13 | BEFORE_REMOVE_LIQUIDITY 1&lt;&lt;9 | BEFORE_SWAP 1&lt;&lt;7 | AFTER_SWAP 1&lt;&lt;6 | BEFORE_SWAP_RETURNS_DELTA 1&lt;&lt;3 | AFTER_SWAP_RETURNS_DELTA 1&lt;&lt;2 (https://github.com/Uniswap/v4-core/blob/main/src/libraries/Hooks.sol). isValidHookAddress는 return-delta 비트에 action 비트 동반과 static fee 0 풀에 ≥1 비트를 요구 — 0x22CC·0x20CC 모두 통과(A1 §2 확인). BaseHook 생성자가 validateHookPermissions를 호출하므로 잘못 마이닝된 주소는 배포조차 안 된다. 훅 주소가 권한을 각인해야 한다는 규칙: https://developers.uniswap.org/docs/protocols/v4/concepts/hooks

스토리지. mapping(bytes32 poolId => PoolTerms{token, tokenIsCurrency0, initialized, initTimestamp})(1슬롯), mapping(address token => bytes32 poolId), mapping(address token => uint256 stranded)(정상 경로에서는 항상 0). immutable: POOL_MANAGER, POSITION_MANAGER, TARGET, ESCROW, LOCKER, TICK_SPACING=200, BASE_FEE_BPS=100, MAX_TOTAL_BPS=9900.

수수료 위치 — 왜 before + after 둘 다인가. v4 스왑은 한 통화를 specified로 지정한다(amountSpecified &lt; 0 = 정확 입력, > 0 = 정확 출력). quote(ETH)는 정확입력 매수·정확출력 매도에서 specified, 정확출력 매수·정확입력 매도에서 unspecified다. beforeSwap의 반환 델타는 specified 쪽에만 스왑 전에 적용되고(amountToSwap += hookDeltaSpecified, Hooks.sol beforeSwap), afterSwap의 반환값은 unspecified에 더해진다(hookDeltaUnspecified += …; swapDelta = swapDelta − hookDelta, Hooks.sol afterSwap). 그러므로 항상 quote로 받으려면 두 콜백이 모두 필요하다. Pons처럼 afterSwap만 쓰면 정확입력 ETH 매수(가장 흔한 거래)에서 수수료가 밈코인으로 들어와 신뢰된 feeSweepOperator가 변환해야 한다(검증 소스 주석 "converted … in a batched sweepPoolFees call") — 우리는 운영자가 없으므로 불가. Clanker ClankerHookV2가 이 4-케이스 패턴이다(launch/hookv2.sol). 커스텀 어카운팅 가이드: https://developers.uniswap.org/docs/protocols/v4/guides/custom-accounting

케이스 specified 징수 위치 알려진 양 총량 G fee 반환
A 정확입력 매수 quote beforeSwap X X X·p BeforeSwapDelta(+fee, 0)
B 정확출력 매수 token afterSwap 풀이 가져간 Q Q/(1−p) ⌈Q·p/(1−p)⌉ int128(+fee)
C 정확입력 매도 token afterSwap 풀이 준 Y Y Y·p int128(+fee)

p = bps/10000, bps = 100 + snipe(t)(매수) 또는 100(매도), capped로 총 ≤ 9900. B·D의 1/(1−p) 보정으로 정확입력·정확출력이 같은 체결에 같은 수수료를 낸다. HookDeltaExceedsSwapAmount는 p ≤ 0.99에서 도달 불가(A1 §2 확인). 캐스트는 SafeCast.toInt128(A1-11).

정산(스왑마다, 배치 없음).

function _collect(bytes32 id, PoolTerms memory t, Currency quote, uint256 fee, uint256 bps, uint256 snipeBps_, bool isBuy, bool exactIn) internal {
    if (fee == 0) return;
    uint256 snipeFee = fee * snipeBps_ / bps;          // 비례 슬라이스
    uint256 baseFee  = fee - snipeFee;
    poolManager.take(quote, address(this), fee);        // 네이티브 ETH가 훅으로 (receive: POOL_MANAGER만)
    try ESCROW.credit{value: fee}(t.token, baseFee, 0, snipeFee) {}
    catch (bytes memory reason) { stranded[t.token] += fee; emit FeeStranded(t.token, fee, reason); }
    emit FeeTaken(id, t.token, isBuy, exactIn, fee * 10_000 / bps, baseFee, snipeFee);
}

take는 콜백 안에서 허용된다(문서의 수수료 예제가 beforeSwap에서 그렇게 함); 훅의 일시적 −fee는 _accountPoolBalanceDelta가 +fee를 크레딧하며 상쇄된다. 에스크로 credit은 등록·바인딩된 토큰에 대해 총함수(revert 없음)로 설계·증명하지만(§3.8), catch는 "불변 시스템에서 수수료 경로가 스왑을 되돌리는 일은 없어야 한다"는 A1-04에 대한 마지막 보루다. flush(token)은 누구나 재시도.

콜백. - beforeInitialize(sender, key, sqrtPriceX96): require(sender == TARGET); terms[id].token != 0 && !initialized; initialized = true; initTimestamp = uint40(block.timestamp); emit PoolInitialized. PoolManager.initialize는 msg.sender를 그대로 넘기므로(Hooks.sol beforeInitialize) PositionManager.initializePool 경유는 거부된다 → 우리 키의 PoolAlreadyInitialized는 도달 불가. - beforeSwap/afterSwap: 위 표. - beforeRemoveLiquidity(sender, key, params, …): sender == POSITION_MANAGER && params.liquidityDelta &lt; 0 && LOCKER.isLockedPosition(terms[id].token, uint256(params.salt))이면 LockedPosition. PositionManager는 _decrease/_burn에서 salt = bytes32(tokenId)를 넘긴다(https://github.com/Uniswap/v4-periphery/blob/main/src/PositionManager.sol; A1 §2 확인). 실제 잠금은 락커의 onlyIfApproved 불통과다; 이 가드는 "훅에서도 검증 가능"하게 만드는 방어 심층. - 나머지 콜백: HookNotImplemented.

register(key, token) onlyTarget. 키 형태 검사(fee == 0, tickSpacing == 200, hooks == this, currency0 == address(0), currency1 == token), poolOf[token] == 0, ESCROW.quoteOf(token) == address(0), ESCROW.venueOf(token) == address(this). 기록 후 emit PoolRegistered.

불변식. 스왑 후 훅의 PoolManager 델타 0; 훅 ETH 잔고 = Σ stranded(정상 경로 0); 토큰당 훅 풀 정확히 1개, 재초기화 불가; 매도 bps ≤ 100 모든 t; FeeTaken.grossQuote·bps/10000 == baseFee + snipeFee.

가스. 베이스 v4 스왑(UR) ≈ 120–150k + 훅 45–55k(콜백 2회, take+전송, 에스크로 SSTORE, 이벤트). ERC-6909 배치는 v1.1 옵션.

4.2 매수·매도·크로싱 정수 산식

매수(정확 입력 g wei, fee f=100, tax c, snipe z bps; 모두 내림):

fee = g·f/1e4;  tax = g·c/1e4;  snipe = g·z/1e4;  net = g − fee − tax − snipe
out = (X0 − S)·net / (V + R + net)                       // 내림 → 커브가 먼지 보유, k' ≥ k
if out ≥ X_SELL − S:                                      // 크로싱
    out     = X_SELL − S
    netNeed = (V + R)·out / (X0 − S − out) + 1             // 올림
    spent   = min( ceil(netNeed·1e4 / (1e4 − f − c − z)), g )
    fee/tax/snipe를 spent로 재계산; net = spent − fee − tax − snipe; refund = g − spent
R += net;  S += out
에스크로: credit{value: fee+tax+snipe}(token, shared=fee, creatorOnly=tax, protocolOnly=snipe)

매도(정확 입력 t 토큰): gross = (V + R)·t/(X0 − S + t)(내림); fee = gross·f/1e4; tax = gross·c/1e4; out = gross − fee − tax; R −= gross; S −= t. gross ≤ R은 t ≤ S에서 대수적으로 보장된다(R − gross = V(S − t)/(X0 − S + t) ≥ 0), 반올림은 R을 키우는 방향.

반올림 방향: 커브가 내보내는 양(매수 토큰, 매도 ETH)은 내림, 매수자에게 요구하는 양(크로싱)은 올림(+1), 수수료는 총량에 내림 → 수수료 버킷이 실제 수령액을 넘지 않는다. 결과 R_final − Q = 2 wei(§4.7), 절대 음수 아님. 먼지 매도(gross &lt; 100 wei)는 수수료 0 — 추출 불가(A1 §2).

4.3 졸업 가격 연속성 증명

커브 마지막 한계가격 p* = (V + R)/(X0 − S*) = (V + R)/X_RES(S* = X_SELL). 타깃은 tokensSeeded = X_RES·R/(V + R)를 R과 짝지어 시딩한다. 풀 개장가 = R/tokensSeeded = R·(V + R)/(X_RES·R) = (V + R)/X_RES = p*. 비(比)가 항등적으로 1이며 반올림이 아니다(R = Q + 2 wei가 21번째 자리를 움직일 뿐, A2 §2.1). sqrtPriceX96 = √(tokensSeeded/R)·2⁹⁶은 Pons PonsV2GraduationMath.sqrtPriceX96FromAmounts와 같은 식. 수수료는 경계 양쪽 모두 ETH 레그 1 %, 매도 서차지 없음, 크로싱 매수자의 환불은 풀 t=0 매수에 99 %가 붙어 재활용 불가 ⇒ 졸업 차익거래 창 없음.
