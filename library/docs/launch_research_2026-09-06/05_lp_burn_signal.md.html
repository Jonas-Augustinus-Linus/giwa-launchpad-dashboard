Is "LP burned" still a valid signal? (Sept 2026) — memo for a memecoin launcher

Observed: 2026-09-06 04:30–05:30 KST (2026-09-05 19:30–20:30 UTC). All Telegram data is from the public previews https://t.me/s/&lt;channel>; all chain data was read directly from public RPCs / Blockscout at that time. Nothing here is investment advice.

0. TL;DR

  • "LP burned" was a Uniswap v2-era signal: an ERC-20 LP token sent to 0x…dead cannot be redeemed, so a 100%-burned pair cannot be pulled. It is still a valid check wherever an ERC-20 LP token exists (Uniswap v2 / PancakeSwap v2 forks, PumpSwap, Raydium CPMM).
  • In Sept 2026 the venues where new memecoins actually launch have moved to v4 (measured: Base ≈87% of new pools in the last 24h are v4; Robinhood Chain ≈92% in the last 6h) and to launchpads with hooks + lockers (Clanker, Zora, Doppler, Pons v2, …). There is no LP token in v3/v4: liquidity is an NFT (PositionManager) or a raw position owned by a contract. "Burned" is the wrong question; the right question is "who owns the position, and is there any code path that can remove it?"
  • The two iPop channels do not report any LP status at all (no burn, no lock, no locker, no hook, no honeypot). They only report chain / launchpad label / ticker / MC / cumulative fee / age / CA. The launchpad label is the only indirect LP hint ("Pons v2" ⇒ locker-owned by construction; "pool_uniswap_v4" ⇒ unknown owner — could be a permanent locker, a time-lock, or a plain EOA).
  • Three alerted tokens traced on-chain show all three cases side by side: NEST (Pons v2) → NFT owned by PonsV2LaunchLocker with no withdraw function; SPRM ("pool_uniswap_v4") → NFT owned by a custom SPRMLiquidityLocker with a withdrawPosition() function whose state happens to be sealed permanent; OTER ("pool_uniswap_v4", MC shown as 5.4M→7.9M) → NFT owned by a plain EOA that can pull liquidity any time.

2. Is "LP burned" still meaningful? — by pool type

2.a Uniswap v2-style pairs (ERC-20 LP token) — still meaningful, but a shrinking minority

Mechanics: the pair mints an ERC-20 LP token; sending it to 0x…dead (or 0x0) makes burn() impossible for that share, so "100% of LP supply burned" ⇒ pool cannot be drained by the deployer. Locking (UNCX/Team Finance v2 lockers) is the time-limited alternative; GoPlus exposes it as lp_holders[].is_locked / locked_detail (docs: https://docs.gopluslabs.io/reference/response-details — lp_holders: "Top 10 LP holders' info including address, is_locked, tag, is_contract, balance, percent, and locked_detail").

2.b Uniswap v3 positions (ERC-721 NFT)

  • Positions are NFTs minted by NonfungiblePositionManager; "Every NFT is identified by a unique uint256 ID inside the ERC-721 smart contract, declared as the tokenId" (https://developers.uniswap.org/docs/protocols/v3/guides/managing-liquidity/getting-started). decreaseLiquidity/collect/burn are callable by the NFT owner/approved — so "burning the LP" means sending the NFT to 0x…dead (fees become unclaimable too), and "locking" means the NFT sits in a locker contract that only allows fee collect until an unlock date.
  • Lockers: UNCX v3 locker docs — https://docs.uncx.network/guides/for-projects/liquidity-lockers-v3.md ; investor check — https://docs.uncx.network/guides/for-investors/liquidity-lockers/how-can-i-check-if-the-project-locked-liquidity.md ("enter the pair address into the searchbar … browse all the details about the liquidity locks for that pair"). Team Finance: landing page advertises "regular and UniSwap V3 LP tokens" and "NFT Liquidity Bonds" (https://www.team.finance/, https://handbook.team.finance/services/token-locks/liquidity-locks.md — "Split Locks", "Lock Transfers", "Partial Claims"; withdrawal after expiry via the "Claims" dashboard). Neither handbook page documents v4.
  • What tools show: GoPlus lp_holders[] carries NFT_list[{NFT_id, amount, in_effect, NFT_percentage}] and is_locked per holder (seen live for CLANKER on Base, 2026-09-06: largest v3 LP holder 0xce0b18f8… is a contract holding NFT #1119330 = 87.6% of LP, is_locked: 0). GMGN ETH panel shows "Locked/Burned" ("the risk of liquidity pool withdrawal", https://docs.gmgn.ai/index/ca-security-checks).
  • Verdict: still a meaningful check, but you must read (NFT owner, locker unlock date, who can collect) — a percentage alone is not enough, and it is not "burned" unless the owner is a dead address.

2.c Uniswap v4 pools — "burned" is the wrong question

Primary docs:

  • PoolManager singleton: "Uniswap v4 uses a Singleton design pattern for the PoolManager", "All pool state and logic are encapsulated within the PoolManager contract"; liquidity is modified "via a periphery contract to handle the locking & unlocking" (https://developers.uniswap.org/docs/protocols/v4/concepts/poolmanager). There is no per-pool contract and no LP token.
  • Positions: minted through PositionManager as ERC-721 ("recipient, // Who receives the NFT"; actions INCREASE_LIQUIDITY, DECREASE_LIQUIDITY, BURN_POSITION, collect = decrease with liquidity 0) — https://developers.uniswap.org/docs/protocols/v4/guides/position-manager . Any contract can also hold raw liquidity in PoolManager without an NFT at all (hook-owned singletons).
  • Hooks: ten permissions (beforeInitialize/afterInitialize, beforeAddLiquidity/afterAddLiquidity, beforeRemoveLiquidity/afterRemoveLiquidity, beforeSwap/afterSwap, beforeDonate/afterDonate) plus four return-delta permissions; "A hook contract must be deployed to an address whose low bits encode exactly the permissions it implements"; "a hook can serve an infinite amount of pools" (https://developers.uniswap.org/docs/protocols/v4/concepts/hooks). A hook with beforeSwap/afterSwapReturnDelta can tax or block swaps; one with beforeRemoveLiquidity can block or allow removals; hook owners can usually change fee parameters.
  • v4 is deployed on Robinhood Chain: PoolManager 0x8366a39cc670b4001a1121b8f6a443a643e40951, PositionManager 0x58daec3116aae6d93017baaea7749052e8a04fa7 (https://developers.uniswap.org/docs/protocols/v4/deployments).

2.d Pump-style graduations (Solana) — LP token exists; burned or platform-locked

  • PumpSwap: "When the coin hits a certain market cap the liquidity from the bonding curve is migrated to PumpSwap (an AMM on Solana). The LP tokens received from the PumpSwap pool are then burnt." (https://github.com/pump-fun/pump-public-docs/blob/main/docs/PUMP_PROGRAM_README.md). migrate "is also permisionless, so anyone can migrate a completed bonding curve". Pool state tracks lp_supply "without burns and lock-ups" and coin_creator accrues creator fees to a creator_vault (docs/PUMP_SWAP_README.md, docs/PUMP_SWAP_CREATOR_FEE_README.md). Note the admin disable(admin, disable_create_pool, disable_deposit, disable_withdraw, disable_buy, disable_sell) flag exists at program level. ⇒ "LP burned" is true by construction for canonical pump pools; the residual risks are token-side (creator/insider supply) not LP-side.
  • Raydium LaunchLab: after graduation "platform_scale + creator_scale is locked through LP-Lock" with Fee Keys, and "burn_scale is burned permanently and has no Fee Key" (https://docs.raydium.io/products/launchlab/overview.md, https://docs.raydium.io/products/launchlab/tips-and-gotchas/lp-fee-distribution.md — since 2026-08-17 the creator share merges into the platform's locked LP). Burn & Earn: "Permanently lock a CPMM or CLMM LP position while retaining the right to claim trading fees via a transferable Raydium Fee Key NFT" — the Fee Key "can be sold on any Solana NFT marketplace" (https://docs.raydium.io/user-flows/burn-and-earn.md). ⇒ "burned" on Solana now often means locked-with-fee-key; GMGN's Solana "Burnt" % ("100% indicating that the project cannot withdraw from the liquidity pool", https://docs.gmgn.ai/index/ca-security-checks) is the right field there.

3. Replacement checklist for v3/v4-era launches (what to verify instead of "burned")

For each new CA, in this order:

  1. Pool version + hook — Dexscreener API labels (v2/v3/v4) and, for v4, the hooks address in the Initialize event (or the pool page). No hook + raw pool ⇒ go straight to step 2. Hook ⇒ resolve its verified name on Blockscout/Basescan (Clanker/Zora/Doppler/Pons/… vs unverified bytecode) and read getHookPermissions(): beforeSwap/*ReturnDelta = can tax/block trades; beforeRemoveLiquidity = can gate removals; check whether the hook has an owner and what set* functions exist (PonsV2MemeHook: 9 onlyOwner setters incl. setHookFeeBps).
  2. Position owner — v3: NonfungiblePositionManager.ownerOf(tokenId); v4: PositionManager.ownerOf(tokenId) where tokenId = salt of the ModifyLiquidity event (sender = PositionManager). Acceptable owners: 0x…dead, a launchpad locker (PonsV2LaunchLocker, ClankerLpLockerFeeConversion), UNCX/Team Finance lockers. Red flag: EOA (OTER) or an unverified contract.
  3. Does the owner contract have a withdraw path? Read the verified ABI: any of withdrawPosition, unlock, decreaseLiquidity, burn, safeTransferFrom(this→…), rescue*, sweep* of the NFT, upgradeable proxy, owner ≠ 0x0. If it has a timelock (lockedUntil, unlockDate), read the value and who can extendLock/transferOwnership. Pons v2 locker: none. SPRM locker: has withdrawPosition but sealed permanent. UNCX/Team Finance: unlock date + lock-owner transferability.
  4. Fee recipient / who earns — Clanker rewardRecipients (80/20 split, admin-changeable recipients), Pons hook protocolFeeShareBps/buybackBurnBps/creator recipient, Raydium Fee Key holder, PumpSwap coin_creator. A fee stream to an EOA ≠ deployer is a clustering signal (ponsvitals: 23% of Pons launches).
  5. Token contract — mint authority, blacklist, pausable transfer, tax, proxy/upgradeable, hidden owner: GoPlus is_mintable, is_blacklisted, transfer_pausable, buy_tax/sell_tax, is_proxy, hidden_owner, can_take_back_ownership, owner_change_balance (https://docs.gopluslabs.io/reference/response-details). Note GoPlus returns nothing useful for Robinhood v4 tokens today; for those, read the verified token source directly on robinhoodchain.blockscout.com.
  6. Supply concentration — Bubblemaps token metrics: Top 10 Adjusted ("top 10 entities (after clustering) adjusted to ignore CEXs, DEXs"), Bundles, Bubblemaps score 0–100, Gini/HHI, Nakamoto coefficient (https://docs.bubblemaps.io/data/api/tokens/metrics.md; chain list includes robinhood, base, bsc, solana). GMGN: Top10 <30% rule, Insiders/Bundlers/Snipers/Dev holdings.
  7. Deployer funding & history — first funding tx of the deployer EOA (CEX vs bridge vs another fresh wallet), prior launches, GMGN "Rug History" ("which rug pull tokens may have been previously launched by the creator").
  8. Copycat pools — the same CA can have several pools (VIBES: 1 v3 + 4 v4; NEST: 30 v4 pairs). Check that the pool you route through is the locked one; small side pools owned by EOAs are normal but should not be where you buy.
  9. Only then MC / cumulative fee / age (the only things the iPop channels give you).

4. What the iPop channels miss (honest list)

  1. Any LP custody information — no burn %, no lock %, no locker address, no unlock date, no NFT owner, no hook name/permissions. Their own description ("허니팟 조심하세요") admits they do no honeypot check.
  2. No liquidity depth — only MC and cumulative fees; a "MC 964.1 M" LIT alert or "MC 5.4 M" OTER alert says nothing about how much ETH is actually in the pool (OTER main pool: $610k; its LP is EOA-owned).
  3. No token-contract audit — mint/blacklist/tax/proxy/owner are absent; on Robinhood v4 tokens GoPlus is empty too, so the launcher must read source on Blockscout himself.
  4. No holder/deployer context — no top-10, no bundler/sniper detection, no deployer funding source, no cluster of fee recipients (ponsvitals shows 23% of Pons launches split deployer vs fee wallet).
  5. Label noise — pool_uniswap_v3 and launchpad_unclassified appear in the "v4" channel; USDC was posted as a new token; the same CA is re-alerted repeatedly; Pons v2 covers both healthy grads and the 82%-flatline population's survivors without distinguishing them.
  6. Copycat pools — the alert gives a CA, not a pool id; the CA may have many pools (VIBES, NEST) with different owners.
  7. Latency and scale — ~1–2 alerts/hour each, 25–36 subscribers, channels created 2026-09-04; they cover only Robinhood (+ a few BSC/Base grads), while Robinhood alone initialises ~4.4k v4 pools per 6 h and Pons launches ~22.8k tokens/day — the channel's filter (which pools get posted) is undocumented.
