A1 — Security review of launchpad v1 design (D1 curve/factory/graduation · D2 v4 hook · D3 locker/escrow/GIWA adapter)

Lens: pre-contest auditor (Code4rena / Cantina warden). Date 2026-09-06 KST. Scope = the three design documents in docs/launchpad_v1_design/, read in full, plus the reference material they cite (launch_research_2026-09-06/01, launch_research_2026-09-06/02, launch_research_2026-09-06/05, verified Pons V2 sources under Pons V2 검증 소스(robinhoodchain.blockscout.com, 저장소 미포함)/). 1. Findings in detail

A1-01 · Critical · Atomic graduation is dead on arrival: guarded self-call

Where. D1 §3.7: "Reentrancy guard: OZ ReentrancyGuardTransient … on buy, sell, claim*, graduate, windDown." D1 §5.1 step 3: inside buy() → try this.graduate(token) {} catch … ("an external self-call so the try/catch boundary is a real call frame"). D1 §5.4: windDown "first re-tries graduate in a try/catch and only proceeds if that reverts".

Defect. buy() holds the transient lock; this.graduate() is a new call frame into the same contract; graduate() is nonReentrant → it reverts with Reentrancy() every time. Consequences: 1. Every crossing buy emits GraduationDeferred and leaves the token Closed. The atomic path never works; every launch depends on a keeper/UI calling graduate() afterwards (a fresh frame, so that call succeeds). Trading is frozen between the crossing block and the keeper's block on every launch. 2. windDown() holds the lock too, so its inner graduate retry also reverts with Reentrancy() — the "only if graduate() is genuinely impossible" precondition is always satisfied. Any token that nobody graduates within 7 days can be wound down (see A1-02 for why that is bad).

Pons hit exactly this and documented the escape: PonsV2BondingCurve.graduate() is "deliberately not nonReentrant … so it stays callable from within buy()'s own guarded frame" and is onlyFactory, with the factory as the trampoline. D1 copied the try/catch shape but not that exception.

Fix (spec).

// buy(): guarded. The graduation attempt goes through an INTERNAL function that
// does not touch the guard; the try/catch boundary is the call into the executor.
function _tryGraduate(address token) private {
    CurveState storage c = _curves[token];
    uint256 r = c.realQuote;
    c.status = Status.Graduated; c.realQuote = 0;              // effects
    TOKEN(token).safeTransfer(EXECUTOR, X_RES);
    try EXECUTOR.graduate{value: r, gas: GRADUATE_GAS}(token, X_RES, r) returns (...) { emit Graduated(...); }
    catch (bytes memory reason) {
        // roll back our own effects; the executor's frame already reverted
        c.status = Status.Closed; c.realQuote = uint128(r);
        // token transfer must also be reverted -> do the transfer INSIDE a self-call
        // frame instead, or have the executor pull via transferFrom inside its own frame.
        emit GraduationDeferred(token, reason, gasleft());
    }
}

Simplest robust shape: keep an external, permissionless, nonReentrant graduate(token) for the retry path, and make the atomic attempt an internal _graduateUnguarded that is also what graduate() calls after taking the lock. The executor must pull the tokens (transferFrom(curve, executor, X_RES) with a pre-set allowance) inside its own frame so that a revert in the executor leaves the curve's token balance intact without manual rollback. Add a Foundry test that a crossing buy from an EOA with gasLimit = estimateGas ends in Graduated, not Closed.

A1-02 · High · WindDown valve is attacker-reachable (EIP-150 gas starvation)

Where. D1 §5.4 / D13: windDown(token) re-opens sells against R ≈ Q if now ≥ closedAt + 7 days and an inner try graduate() reverts.

Attack. The caller controls the gas of the inner attempt (63/64 rule). Call windDown with a gas limit such that the inner graduate runs out of gas (≈ 1 M needed; give it 200 k). The catch fires, the "graduation is impossible" predicate is satisfied, status → WindDown. From then on graduate() reverts (NotClosed), sells drain R along the curve, the pool is never created, the locker never receives a position. Pre-condition: the token sat Closed for 7 days — trivially true for any token whose crossing buyer set a low gas limit (or, with A1-01 unfixed, for every token) and that nobody bothered to graduate. Expected victims: long-tail tokens; but the effect is that the system's central promise ("liquidity permanently locked") is per-token falsifiable by a single unprivileged call, and the resulting state is indistinguishable on-chain from a "bricked v4" case.

Even with correct gas handling, the valve makes "no admin" weaker, not stronger: it is an unprivileged state transition that contradicts the graduation promise, gated only by 7 days of inattention.

Fix. Preferred: drop WindDown (owner OQ 6) — the only realistic trigger is a bug in immutable code, and "holders can always sell along the curve" is a worse story than "deploy v2". If kept:

uint256 constant GRADUATE_GAS = 3_000_000;     // ≥ 2× measured graduation gas
function windDown(address token) external nonReentrant {
    ...
    if (gasleft() &lt; GRADUATE_GAS * 64 / 63 + 100_000) revert InsufficientGas();
    try this.graduateUnguarded{gas: GRADUATE_GAS}(token) { return; }   // succeeded → done
    catch (bytes memory reason) {
        if (reason.length == 0) revert NotProvenBroken();   // OOG / empty revert never counts
        ...
    }
}

and lengthen the grace to ≥ 30 days, require ≥ 3 failed attempts in distinct days recorded on-chain, and allow graduate() from WindDown (re-closing sells) so that a transiently broken executor does not permanently strand the pool.

A1-03 · High · "No bundles by construction" is not true at 1-second timestamp granularity

Where. D1 §3.4 "no exempt list ⇒ no bundles by construction"; D1 D7; D2 §4 "No exemptions".

Analysis. Snipe tax is a function of block.timestamp − launchedAt (whole seconds). The launcher controls when the launch tx is submitted and can observe the sequencer's timestamp flips (10 blocks per second on Robinhood). Launch at wall-clock .8 of second S; send the second-wallet buy immediately; it lands in second S+1, 0.1–0.3 s after launch, before any human can react: - Curve, coarse schedule T=3: 9900 >> floor(1·14/3) = 9900 >> 4 = 618 bps → 6.2 %. - Curve with D1's arbBlockNumber interpolation: elapsed clamps to tsMs + 999 once ≥ 10 blocks have passed → n = 37 eighth-halvings → ≈ 4 %; and this is reachable inside the launch second if 10 blocks are produced (the interpolation can only lower the tax). - Pool (D2 staircase): t=1 → 25 %. Compare: Pons's exempt list lets a creator pre-clear 32 wallets at 0 %; ours costs 4–6 % on the curve — a price every real bundler pays gladly (Bags/Pons bundles routinely pay 10 %+ in slippage). The dev-buy exemption is irrelevant to this; the schedule's t=1 level is the whole story. The claim should not be made in that form to Korean retail.

Fix. (a) Rephrase the guarantee as "every non-disclosed buy in the first N seconds pays ≥ X %" and pick X deliberately: with the coarse schedule, T=5 gives 24.75 % at t=1, 3.1 % at t=2 (Pons's documented schedule); or add a floor shelf: taxBps(t) = max(schedule(t), 5000) for t ≤ 1. (b) Anchor the clock to launchedAt + 1 so second 0 and second 1 are the same 99 % tier (D3 §5.2 already suggests it), which makes the launcher's timing trick useless and costs humans nothing (nobody reacts in < 1 s). (c) Same for the post-graduation staircase: [9800, 9800, 2400, 200] anchored to initTimestamp. (d) Keep the schedule identical across curve, hook and pair (see A1-05).

A1-04 · High · Escrow revert = every hooked pool bricked forever

Where. D2 §3.3 _collect → ESCROW.accrue{value} inside the swap; D2 §11 risk 7 acknowledges "any bug in accrue bricks swaps on every pool of this hook forever". D3 §2.3 credit: if (l.creator == address(0)) revert NotRegistered(); if (l.quote != address(0)) revert WrongQuote();. D3 §3.6: "the escrow's credit wraps to WETH9 when ledger.quote == WETH9" — contradicts §2.3, which reverts in that case.

Reachable triggers as specified. 1. register(token, quote, creator) with creator == 0 (D1 §4: "0 ⇒ launcher" is the factory's rule; the escrow itself accepts 0) → l.creator == 0 → NotRegistered on every credit → the curve's first trade reverts (or, if the curve keeps its own ledger per D1, the first pool swap reverts). Immutable, per token, forever. 2. Quote mismatch: hook passes native (credit{value}), GIWA ledger says WETH9 → WrongQuote (D3 §2.3) → every pair swap on GIWA reverts. D3 §3.6's "wrap inside credit" is the intended behaviour but is not what the sketch does. 3. Registration ordering: if escrow.register is not in the same tx as createToken (D3 says "in the launch tx" — D1's createToken sequence never calls it), a token can exist on the curve with no ledger.

Fix. Make credit total for registered tokens and make registration impossible to get wrong: - register: require(creator != 0 && (quote == address(0) || quote == WETH9)); called from createToken in the same tx; hook.register(key, …) and LaunchPairTarget.graduate must require(escrow.quoteOf(token) == &lt;this venue's quote>) before initialize/new LaunchPair. - credit{value}: if l.quote == WETH9 → WETH9.deposit{value}() then accrue; never revert on msg.value == 0 (return) — consistent with §3.6. - Invariant test: for every registered token and every venue, credit/creditToken never reverts except on NotRegistered; fuzz the hook against a mock escrow that reverts to prove the failure mode is understood, then prove the real escrow has no revert path other than solvency. - Consider the ERC-6909 fallback D2 mentions: if accrue reverts, mint claims to the hook instead of reverting the swap (a permissionless flush later). That removes the single-point-of-failure at ≈ +20 k gas. I recommend it for v1 given "no rescue path".

A1-06 · Medium · GIWA pair: non-computable address and a fee double-pay in the sketch

Where. D3 §3.5 new LaunchPair{salt: token}(token, WETH9, LOCKER, ESCROW, uint64(block.timestamp)); D3 §3.4 pairFor "pure CREATE2 computation"; D3 §3.3 swap sketch does token1.safeTransfer(escrow, f); escrow.creditToken(token0Addr, f) while creditToken pulls f via safeTransferFrom(msg.sender).

Defects. (1) Constructor args are part of the CREATE2 initcode hash; openedAt is the graduation timestamp, so the address is unknown until graduation and pairFor(token) cannot be a pure function. (2) Push + pull sends 2f out of the pair but _update(…, b1 − f) records f — reserve exceeds balance; the next buy computes q = b1 − r1 → underflow revert; the pair is bricked until someone calls sync(), which lowers r1 (so the "sync can never lower reserves" statement is false in this state) and reduces k by exactly the leaked amount each swap. The escrow gets paid twice from LP funds until then.

Fix. Constructor takes only (token); WETH9, LOCKER, ESCROW come from the deployer via an immutable read of msg.sender (ILaunchPairTarget(msg.sender).weth9() …) or from a bytes32-free initialize callable once by the deployer; openedAt is set in mint(). Pick one crediting mode (pull with a one-time max approval is cleanest: escrow.creditToken(token, f) only). Invariant: balanceOf(pair) ≥ reserve for both tokens after every function.

A1-07 · Medium · GIWA pair opening price manipulable by pre-graduation donation

Where. D3 §3.3 "Shares minted = sqrt(r0 · r1)" from balances; D3 §3.5 pair address is CREATE2(target, token) — predictable before it exists.

Attack. Anyone can send tokens (bought on the curve) to the future pair address. At graduation mint reads balances → reserves (T + D, E) → opening price lower than the curve's end price by T/(T+D). The donor loses D, but on a fee-ordered sequencer the donor can bid to be the first pool buyer and recover most of it at the discounted price; every other holder is marked down. Pons's v4 executor comment ("a donation cannot move the price the pool opens at") exists because they use explicit amounts; the v4 path here is fine (explicit MINT_POSITION amounts and explicit sqrtPriceX96), the GIWA path is not.

Fix. mint(uint256 amount0, uint256 amount1) sets reserves to exactly the amounts the target transferred; any excess balance is not captured as reserve at mint (it will be captured by the first swap as input — equivalent to skim to the first swapper, which is acceptable and matches v2 semantics for stray balances). Test: donate before graduation → opening price equals curve end price to 1 wei.

A1-08 · Medium · arbBlockNumber interpolation measures load, not time; the table is wrong

Where. D1 §3.4 (Robinhood clock): blkMs = (arbBlockNumber − launchBlock)·100, elapsedMs = max(tsMs, min(blkMs, tsMs + 999)).

Analysis. Arbitrum docs: "block production only occurs when there are transactions to sequence"; D1's own probe measured 0.07 s/block under load and 10 blocks/s at rest. The block clock therefore runs ≈ 1.4× wall-clock precisely during a launch (when bots spam), i.e. the tax decays faster exactly when it should not; the clamp only prevents crossing into the next second. A launcher can also spam its own cheap txs to advance the block clock inside the launch second (each sequenced tx can close a block on Orbit chains). The design's numbers are also mis-stated: with 14 halvings over 3 s, 0.4 s = 1.87 halvings → ≈ 29 % (not 49.5 %), 0.6 s → ≈ 14 % (not 24.7 %), 1.0 s → ≈ 4 % (not 6.2 %). Finally the precompile is a chain-specific dependency in an otherwise chain-agnostic curve and is inconsistent with D2's integer staircase on the same chain.

Fix. Drop the interpolation. Use one integer-second staircase for curve, hook and pair ([9900, 9900, 2400, 200] anchored at launchedAt, per A1-03), documented as "whole seconds since launch, ≈ 10 Robinhood blocks / 1 GIWA block per step". If sub-second resolution is wanted, nominal 100 ms is the wrong constant — but the honest statement is that no on-chain clock on Nitro resolves below the sequencer second.

A1-09 · Medium · Graduation reverts on its own dust forwarding / missing receive()

Where. D1 §5.2 step 6: SWEEP(ETH, EXECUTOR) then CURVE.creditProtocolFees{value}() — "never revert on dust". D1 §3.7 guards claim*; D3's UniswapV4Target sketch has no receive().

Defects. (1) SWEEP sends native ETH to the executor via call; without receive() the PositionManager call reverts → graduation reverts (Pons's executor has receive() external payable {} for this exact reason). (2) The executor is inside the curve's guarded buy → graduate frame; if creditProtocolFees is nonReentrant (it is a claim*-family function per D1) the dust forward reverts → graduation reverts → Closed → A1-02 territory. (3) D3 forwards the dust to escrow.credit(token) instead — fine, but must be the same choice everywhere.

Fix. Executor has receive() restricted to POSITION_MANAGER/POOL_MANAGER; dust goes to the escrow (credit{value}(token)), never back into the curve; the curve exposes no payable function except buy/open. Pons's low-level-call-and-report pattern for the residual sweep is the right shape.

A1-10 · Medium · Creator-recipient lifecycle edge cases

Where. D3 §2.4–2.5.

  1. Compromised creator key: attacker claims accrued fees instantly and proposes a new recipient; the creator can only cancel — a permanent stalemate where neither side can rotate the key and the attacker keeps claiming every new accrual. D3 acknowledges the stalemate but not that the stream is lost, not just the balance. Mitigation lives outside the contracts (recipient = Safe from day one); state it in the launch UI as a required step, not a recommendation.
  2. Lost creator key: 80 % of every future fee for that token is unclaimable forever; there is no protocol-side CTO path by design. Disclose.
  3. claim(token) when l.creator == PROTOCOL: the if (msg.sender == l.creator) branch always wins; the protocol share can only be moved by claimFor. Fix: claim(token, role) with an explicit role argument.
  4. proposeCreator while a proposal is pending silently replaces it and resets pendingEta — fine, but emit CreatorProposalCancelled first so indexers see the old one die.

A1-11 · Low · Hook fee take timing and casts

take in beforeSwap/afterSwap is paid out of the PoolManager's pooled ETH before the swapper settles (Universal Router settles after the swap). A t=0 exact-in buy of X with fee 0.99 X larger than the PoolManager's total ETH balance reverts with an opaque CurrencyNotSettled/transfer failure — benign (the sniper loses gas), but the UI/Quoter should not show it as a hook bug. Unchecked int128(int256(fee)) and uint128 casts: fee can be 99× the pool delta in case B/D; use SafeCast.toInt128. Also the hook needs receive() accepting only POOL_MANAGER (stray ETH is otherwise stuck, harmless).

A1-12 · Low · Locker negative-test list gaps

Add to N1: isValidSignature (ERC-1271 — IERC721Permit_v4.permit/permitForAll verify contract owners through it; absence is the property), permitForAll, subscribe, unsubscribe. Reword N9: onERC721Received gated to positionManager stops foreign collections, not foreign positions; any PositionManager NFT can still be safeTransferFrom'd into the locker and is then stuck — harmless, but lockInfo-driven verifiers are unaffected only because lockV4Position is target-only and checks ownerOf. Keep D1's "no ERC-1271" explicitly in the spec.

A1-13 · Low · Permissionless credit and cheap wash volume

Anyone can credit{value}(token) and mint a FeesAccrued event for any token — the DefiLlama adapter in D3 §2.6 sums all of them, so "protocol revenue" and per-token creator revenue are spoofable at the cost of the spoofed amount (which still goes to the recipients — cheap if the spoofer is the creator). With a 2 % creator tax and 80 % fee rebate, a creator wash-trading their own curve pays ≈ 0.2 % per trade net. Fix: keep credit permissionless (no privilege to gate) but index source and filter dashboards to {curve, hook, pair}; consider restricting credit to registered sources anyway (D2's choice) — there is no legitimate third-party crediting use case in v1.

A1-14 · Low · Pair hygiene

A1-16 · Low · Same-address story: what CREATE3 does and does not guarantee

Confirmed against CreateX source: permissioned salt with flag byte 0x00 → guardedSalt = keccak256(bytes32(uint160(msg.sender)) ‖ salt) (D1's formula is exact; D2/D3's abi.encode(msg.sender, salt) produces the same bytes). CREATE3 address = f(CreateX, guardedSalt) and is bytecode-independent. Consequences to state in docs: (1) on any chain where the owner EOA has not yet deployed, the owner (and only the owner) can place any code at the escrow/locker/factory/curve addresses — "same address" ≠ "same code"; verifiers must compare extcodehash per chain; (2) the owner EOA therefore remains a privileged key for as long as unclaimed chains exist (GIWA mainnet 9134); a leak lets an attacker squat the canonical addresses on new chains — keep it in a hardware wallet and consider burning the remaining salts by deploying the real contracts on 9134 at genesis+1; (3) tokens: the factory's permissioned salt binds msg.sender == factory, so a stranger cannot pre-claim a token address on chain B; but the launcher's chain-B token is only issued if the same factory code is there — again an owner-honesty point; (4) deployCreate2 for the hook: CreateX is the CREATE2 deployer and applies _guard to the salt, so HookMiner must iterate the 11 entropy bytes and hash with deployer = CreateX, salt = guardedSalt — D2 §5.2 has this right; D3 §4.2's Arachnid path does not apply the guard (pick one — A1-05 #8).

A1-18 · Info · Narrative risks worth deciding consciously

  • Dev buy is sent to msg.sender; a contract launcher receives it and may split it in the same tx (still ≤ 5 %; the DevBuy event names the contract). Either accept and document, or require msg.sender == tx.origin-free alternative: none exists that is not itself a footgun — accept.
  • Overhang as a locked single-sided position (D1 D11) is a permanent ask wall of ≈ 40 % extra depth starting ≤ 2 % above the graduation price; GMGN-style tools will show the locker as an 8.16 % holder. Burn (D3-8) avoids both at the cost of the "exactly 1e9" story. Security-neutral; decide before audit (A1-05 #4).
  • The crossing buyer (≈ 33 % of supply in D1's worked example, bought at ≈ 46 % of the pool's opening price) can dump into the fresh pool at t=0 paying only 1 % (sells are never snipe-taxed). Inherent to the Pons shape; document that "post-graduation snipe tax" protects against buyers only.

2. Things I checked that hold up (so the auditor after me does not re-derive them)

  • Hook delta accounting (D2 §3): verified against Hooks.beforeSwap/afterSwap source: amountToSwap += hookDeltaSpecified with the sign-flip guard; hookDelta orientation (amountSpecified &lt; 0 == zeroForOne) ? (specified, unspecified) : (unspecified, specified); swapDelta -= hookDelta; the hook's transient −fee from take nets against +fee credited via _accountPoolBalanceDelta. All four cases in D2 §3.1 are correct, including the p/(1−p) exact-out normalisation, and HookDeltaExceedsSwapAmount is unreachable with bps ≤ 9900.
  • beforeInitialize gate: initialize passes msg.sender to the hook; PositionManager.initializePool would present the PositionManager as sender and is therefore rejected; PoolAlreadyInitialized for our key is unreachable. Flags: isValidHookAddress requires return-delta bits to accompany action bits and ≥ 1 bit for a static-fee pool — 0x22CC and 0x20CC both pass.
  • beforeRemoveLiquidity guard: PositionManager's _decrease/_burn use salt = bytes32(tokenId) and sender == PositionManager — the guard matches. It is defence-in-depth only; the real lock is onlyIfApproved + a locker that never approves and has no ERC-1271.
  • Locker custody: PositionManager mints with _mint (no receiver callback), nextTokenId is public and pre-incremented, so tokenId = nextTokenId() read before modifyLiquidities is right; ownerOf check after is the proof. No CALL in the locker's runtime code is achievable and provable (N4).
  • Curve rounding: every outbound amount floors, the crossing buy ceils netNeed and grosses up with ceil, fees floor on the gross leg → k' ≥ k, R_final ≥ Q (minus the min(spent, g) wei edge, which only leaves R a wei short — harmless), buy-then-sell never returns more than spent. Dust sells with gross &lt; 100 wei pay zero fee — not extractable.
  • Curve reentrancy surface: LaunchToken is plain OZ (no hooks), ETH out only via call after effects, refund to msg.sender not recipient; a reverting receiver only hurts itself. Refund after the graduation attempt is the right order.
  • Sniper multi-wallet / contract callers: time-based, so splitting does not help; the cap ≤ 10000 − f − c − 100 keeps exact-out finite.
  • CreateX same-chain front-run: entropy is msg.sender-namespaced and CreateX's guard binds the factory; a copied calldata lands elsewhere. Cross-chain squat impossible for third parties (A1-16 caveats are about the owner, not attackers).
  • Native ETH as v4 currency0: address(0) always sorts first; avoids the upgradeable aeWETH proxy on Robinhood — correct call.
  • Gas: 32 M per-tx cap on Nitro vs ≈ 1.1 M graduation; not a DoS vector. Griefing the atomic path only self-defers (once A1-01 is fixed).
  • Escrow CEI: balances zeroed before call; nonReentrant; claimFor reads recipients from storage; receive only from WETH9. Solvency invariant is well-formed.
