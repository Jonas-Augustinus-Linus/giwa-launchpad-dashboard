Deployment order per chain (all via CreateX CREATE3 from the owner EOA, salt byte 21 = 0x00 so the same address is produced on every chain): predict all five addresses first, then deploy PermanentLocker, LaunchHook (Robinhood only; its address must additionally carry the BEFORE_INITIALIZE | AFTER_SWAP | AFTER_SWAP_RETURNS_DELTA bits — mined salt, so the hook is CREATE2-mined per chain and not address-identical, which is fine because pools are chain-local), GraduationExecutor, BondingCurve, LaunchFactory. Circular immutables (curve ↔ factory) are resolved by passing predicted addresses into constructors; each constructor asserts the counter-party's address matches once deployed (a wire()-free design: the last-deployed contract's constructor performs a read-back check require(curve.factory() == address(this))).

Why the factory must be address-identical: the token address under CREATE3 is f(CreateX, guardedSalt) and CreateX's permissioned guard folds msg.sender (= our factory) into guardedSalt. If the factory were at different addresses, the token addresses would differ. The curve, executor and locker may differ per chain (they hold chain-specific immutables anyway), but deploying them through the same guarded-CREATE3 path costs nothing and keeps the ops story simple.

2. LaunchToken

2.1 Requirements → code shape

  • Fixed supply 1_000_000_000e18, 18 decimals, minted once, in the constructor, to the curve singleton. No owner, no mint, no pause, no blacklist, no transfer hooks, no fee-on-transfer.
  • Runtime bytecode identical for every launch and on both chains: no immutables at all in the token (an immutable is inlined into runtime code; OZ ERC20 stores _name/_symbol in storage so plain OZ is fine; OZ ERC20Permit/EIP712 would inline _hashedName, _cachedDomainSeparator, _cachedThis as immutables — see the cited EIP712.sol — so Permit is out unless we write a storage-only EIP-712 variant. Not worth it: Permit2 is canonical on both chains and the Universal Router uses it).
  • ERC20Burnable retained (≈ 200 bytes) so any holder can burn and so the executor/hook can burn token-side dust or fees without a dead-address transfer (owner rule: "token-side fees retained or burned").
  • Metadata (logo, description, socials) is not stored on the token; the factory emits it in TokenCreated (calldata → log). This keeps the token at ≈ 2.4 KB runtime and launch gas low. Name ≤ 64 bytes, symbol ≤ 16 bytes (Pons's caps); note ≤ 31 bytes keeps each in a single slot (Korean UTF-8 is 3 bytes/char → 10 chars).
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.26;

import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {ERC20Burnable} from "@openzeppelin/contracts/token/ERC20/extensions/ERC20Burnable.sol";

/// @notice Fixed-supply meme token. Entire supply is minted to the launchpad's bonding curve.
///         No owner, no mint, no pause, no hooks, no immutables (runtime bytecode is identical for every launch).
contract LaunchToken is ERC20, ERC20Burnable {
    uint256 public constant SUPPLY = 1_000_000_000e18;
    /// @dev stored, not immutable, so runtime code stays identical across launches/chains.
    address public launchpad; // the BondingCurve singleton that received the supply (indexers use it)

    constructor(string memory name_, string memory symbol_, address curve_) ERC20(name_, symbol_) {
        launchpad = curve_;
        _mint(curve_, SUPPLY);
    }
}

Bytecode identity check: type(LaunchToken).runtimeCode has no immutable references; constructor args live only in creation code. Blockscout matches new deployments to an already-verified bytecode twin (verified_twin_address_hash field in its /api/v2/smart-contracts/{addr} response, seen on the Pons JSON) — so after verifying the first token, every later token shows as verified with decoded constructor args.

2.2 Same address on 4663 and 9134/91342 — salt scheme and front-running

CreateX rules (README): salt layout [20 bytes deployer][1 byte flag][11 bytes entropy]. - deployer bytes == msg.sender and flag 0x00 → "solely a permissioned deploy protection", guardedSalt = hash(msg.sender, salt). Only that sender can ever land that address, on any chain. - deployer bytes == msg.sender and flag 0x01 → also mixes block.chainid → different address per chain — we must not use it for the token. - deployer bytes == zero and flag 0x00 → guardedSalt = keccak256(abi.encode(salt)), unguarded: anyone on chain B can pre-deploy garbage at "our" address → rejected. - flag > 0x01 → InvalidSalt revert. - deployCreate3 "deploys via the CREATE3 pattern (i.e. without an initcode factor)"; computeCreate3Address(bytes32 salt) / (salt, deployer) are the predictors. README: "we strongly recommend implementing a permissioned deploy protection by setting the first 20 bytes equal to msg.sender in the salt" (to prevent cross-chain front-running).

Our scheme (factory is msg.sender to CreateX):

function _tokenSalt(address launcher, bytes32 userSalt, string calldata name, string calldata symbol)
    internal view returns (bytes32 salt)
{
    bytes11 entropy = bytes11(keccak256(abi.encode(launcher, userSalt, keccak256(bytes(name)), keccak256(bytes(symbol)))));
    // [ factory (20) ][ 0x00 (1) ][ entropy (11) ]
    salt = bytes32(bytes20(address(this))) | (bytes32(entropy) >> 168);
}
// guardedSalt as CreateX computes it for (MsgSender, flag 0x00): keccak256(abi.encodePacked(bytes32(uint256(uint160(msg.sender))), salt))
// (mirror CreateX._guard exactly in predictTokenAddress; verify against the deployed CreateX source before shipping)
function predictTokenAddress(address launcher, bytes32 userSalt, string calldata name, string calldata symbol)
    external view returns (address)
{
    bytes32 guarded = keccak256(abi.encodePacked(bytes32(uint256(uint160(address(this)))), _tokenSalt(launcher, userSalt, name, symbol)));
    return CREATEX.computeCreate3Address(guarded, address(CREATEX));
}

Threat analysis: - Cross-chain squat (attacker sees the launch on Robinhood, races to claim the same address on GIWA): impossible — only our factory (same address on both chains, only deployable by the owner EOA's guarded salt) can produce that guardedSalt, and the factory only does so for msg.sender == launcher with the same (userSalt, name, symbol). - Same-chain salt front-run (attacker copies calldata to grab the launcher's predicted address): the entropy is namespaced by msg.sender, so a copied call lands at a different address. (Pons does the same: _launchSalt = keccak(originalDeployer, salt), comment: "any caller may name an arbitrary payout address and could otherwise squat another creator's deployment".) - Launcher re-uses a salt: CREATE3 proxy already exists → CreateX reverts (FailedContractCreation); the factory checks predictTokenAddress(...).code.length == 0 first to give a clean SaltAlreadyUsed() error. - Different metadata on chain B: because keccak(name)/keccak(symbol) are in the entropy, the same address implies the same name/symbol on both chains — the address is a commitment to the ticker. - 11-byte entropy = 2^88 space; collisions are irrelevant because the namespace is already launcher-bound. - Why not plain CREATE2 from the factory: the token's init code contains the curve address (chain-specific) → different address per chain unless the whole stack were address-identical; CREATE3 makes the address independent of init code, and CreateX is already deployed and audited on both chains. Cost: one extra CALL + a 16-byte proxy deploy (≈ 50–60k gas) per launch.

Cross-chain trap worth stating in ops docs: the launcher must call createToken from the same EOA on both chains. Smart-account launchers (ERC-4337) are fine as long as the account address is the same on both chains.

3. BondingCurve (singleton)

3.1 Singleton vs per-launch — decision

Singleton (chosen) Per-launch clones (EIP-1167) Per-launch full contracts (Pons)
Launch gas ≈ 3 fresh slots ≈ 66k + registry ≈ 45k clone + init SSTOREs ≈ 2.5–3.2M (measured 3.71M with token)
Trade gas direct SSTOREs on warm mapping + DELEGATECALL (≈ 2.6k) + cold code same as singleton, cold code load
Blast radius of a bug all curves' ETH in one balance isolated balances, shared logic isolated balances, shared logic
Indexing one address, token indexed in events one address per token one address per token
Bytecode must stay < 24,576 B → trading only same Pons had to split into 5 helper contracts

The singleton wins on gas (≈ 3.5× cheaper launches; with 25k launches/day on Pons, most of them bots, per-launch cost is the product's price tag) and operational simplicity. The "one balance" risk is real and is mitigated structurally: every ETH movement is bounded by a per-token accounted amount (R, creatorFees[token]) or the global protocolFees; nothing ever reads address(this).balance to decide a payout; and the invariant address(this).balance ≥ Σ R_i + Σ creatorFees_i + protocolFees is a fuzz/invariant test target. Donated tokens/ETH are ignored by the accounting (they are simply stranded, as in Pons's graduate() comment "a donation cannot move the price the pool opens at").

3.2 Math

Notation (all in wei / 18-dec units): - X0 = 1e27 supply on the curve at launch (constant), V virtual quote (immutable), Q graduation threshold (immutable). - R real ETH held for the token (excludes fees), S tokens sold so far, curve token balance = X0 − S. - Invariant: (V + R)·(X0 − S) = k = V·X0, i.e. R(S) = V·S/(X0 − S), S(R) = X0·R/(V + R). - Marginal price p(S) = (V+R)/(X0−S) = V·X0/(X0−S)^2 ETH per token.

Graduation point and the general relation between X0, V, Q: - Trigger at R = Q ⇔ S* = X_sell = X0·Q/(V+Q); reserved (never sold) X_res = X0 − X_sell = X0·V/(V+Q). - With r = Q/V: sold fraction r/(1+r), so 71.43 % ⇔ r = 2.5; V = 1.68 ⇒ Q = 4.2 (Pons). Final price p* = (V+Q)^2/(V·X0), graduation FDV = (V+Q)^2/V, start FDV = V, price multiple curve-start→graduation = (1+r)^2 = 12.25×. - Pool seed at p*: ETH Q, tokens Q/p* = X0·V·Q/(V+Q)^2 (20.41 %), overhang X_res − that = X0·V^2/(V+Q)^2 (8.16 %).

Buy (exact input, gross g wei of ETH, fee f, creator tax c, snipe z, all bps):

fee   = g·f / 10000            (floor)
tax   = g·c / 10000            (floor)
snipe = g·z / 10000            (floor)
net   = g − fee − tax − snipe
out   = (X0 − S)·net / (V + R + net)          (floor → curve keeps dust, k' ≥ k)
if out ≥ X_sell − S:                          (crossing buy)
    out      = X_sell − S
    netNeed  = (V + R)·out / (X0 − S − out) + 1                     (ceil)
    spent    = ceil(netNeed·10000 / (10000 − f − c − z)),  min(spent, g)
    recompute fee/tax/snipe on `spent`; net = spent − fee − tax − snipe
    refund   = g − spent
R += net;  S += out;  creatorFees[token] += (fee+snipe)·8000/10000 + tax;  protocolFees += rest

Sell (exact input t tokens):

gross = (V + R)·t / (X0 − S + t)      (floor)
fee   = gross·f / 10000 ; tax = gross·c / 10000
out   = gross − fee − tax
R −= gross ;  S −= t ;  accrue fee/tax as above

Rounding direction: every amount paid out by the curve (tokens on buy, ETH on sell) is floored; every amount required from the buyer (crossing buy) is ceiled (+1). Fees are floored on the gross leg, so fee buckets never exceed what was actually received. Consequence: R at the crossing point is Q plus at most a few wei (worked example below: R_final − Q = 2 wei), never below.

Invariants (fuzz targets): 1. (V+R)(X0−S) ≥ V·X0 after every trade; equality at launch. 2. S ≤ X_sell; R ≤ Q + dust while status == Trading. 3. token.balanceOf(curve) ≥ X0 − S (equality unless someone donates tokens). 4. curve.balance ≥ Σ R + Σ creatorFees + protocolFees. 5. A buy followed by the immediate sale of the same tokens returns ≤ the ETH spent (fees + rounding), never more. 6. status moves only Trading → Closed → Graduated, or Closed → WindDown after the grace period.

Slippage: buy(token, minTokensOut, recipient, deadline) uses Pons's price-bound check spent·minTokensOut ≤ received·tokensOut so a partial (crossing) fill honours the caller's price rather than failing; sell(token, tokensIn, minEthOut, recipient, deadline) uses a plain out ≥ minEthOut. deadline is block.timestamp-based (1 s granularity on both chains).

3.3 Fees on the curve

  • Trading fee 100 bps on the ETH leg both ways; split 8000 / 2000 bps creator / protocol at accrual time (integer split, protocol gets the remainder so the two shares sum exactly).
  • Creator tax 0–200 bps, chosen at createToken, immutable, curve phase only, 100 % to creatorFees[token] (Pons applies it on curve swaps only; we copy that so the post-graduation pool has a single, uniform 1 % hook fee).
  • Snipe tax joins the trading-fee bucket (80/20). Considered and rejected: (a) 100 % to protocol — invites "the protocol profits from bots" criticism and misaligns with Pons, whose docs say the tax "joins the launch's trading fee"; (b) donate it to R — would break invariant 1 (k would drift), move the graduation seed price, and make the crossing-buy math config-dependent. Creator self-sniping is unprofitable: 99 % tax, 80 % of which returns to the creator ⇒ net loss ≥ 20 % of the spend for ~1 % of the tokens.
  • Creation fee 0.0005 ETH is accrued to protocolFees (not pushed) — one fewer external call in createToken and no revert vector.
  • Claims are pull-based, callable by anyone (funds always go to the registered recipient): claimCreatorFees(token) pays factory.creatorRecipient(token); claimProtocolFees() pays the immutable PROTOCOL_RECIPIENT. Payout via call{value}; a reverting recipient just fails the claim and keeps the balance accrued — the creator's remedy is the 3-day recipient change.
  • The protocol recipient is an immutable constructor argument of the curve (and of the hook); there is no setter.

Fee accrual is two warm SSTOREs per trade (creatorFees[token], protocolFees) — no escrow call. If the escrow/claim UI component wants a single claim surface across curve + hook, it reads both contracts; the curve does not push.

3.4 Snipe tax

Formula (Pons's, verified in currentSnipeTaxBps): taxBps(t) = START >> floor(t·H / T) with START = 9900, H = 14 halvings (2^14 > 9900 ⇒ reaches 0 inside the window), T = window seconds, t = elapsed since launchedAt. Then taxBps = min(taxBps, 10000 − f − c − 100) so the buyer always keeps ≥ 1 % of the spend (avoids a zero-denominator gross-up and a 100 % take).

Block-timestamp granularity, chain by chain: - Robinhood (Nitro, ~0.1 s blocks): measured 10 blocks per timestamp second; block.timestamp is "updated every child chain block based on the sequencer's clock", monotonic, bounded to [−24 h, +1 h] of real time (Arbitrum docs). The launch second therefore spans ~10 blocks at 99 %, and the next second drops to 6 % — an FCFS bot that lands at t=1 pays 6.18 % (worked example: 0.5 ETH at t=1 buys 20.5 % of supply for 0.031 ETH tax). To make the decay actually exponential at block resolution, the Robinhood curve interpolates inside the second with ArbSys(0x64).arbBlockNumber() (own-chain height; block.number is the Ethereum height and moves every 13–15 s, per Arbitrum docs and confirmed by the 25.9M vs 55.5M reads above):

tsMs = (block.timestamp − launchedAt) · 1000 blkMs = (arbBlockNumber() − launchBlock) · 100 // nominal 100 ms per block elapsedMs = max(tsMs, min(blkMs, tsMs + 999)) // blocks refine within the current second, never past it n = elapsedMs · H · 8 / (T · 1000) // eighth-halvings taxBps = (START · FRAC8[n % 8]) >> (n / 8), FRAC8[i] = floor(2^(−i/8) · 2^16) / 2^16 With T = 3: 99 % → 49.5 % at 0.4 s → 24.7 % at 0.6 s → 6.2 % at 1.0 s → 0.8 % at 1.6 s → 0.2 % at 2.0 s → 0 at 3.0 s. Blocks come faster than 100 ms when busy (0.07 s measured) — the tsMs + 999 clamp stops the block clock from running ahead of wall time; quiet periods (no blocks) fall back to the timestamp floor. This is the only chain-specific code in the curve, isolated behind an IClock immutable (RobinhoodClock uses ArbSys; GiwaClock returns tsMs). - GIWA (OP Stack, 1 s blocks): all transactions in a block share one timestamp; Flashblocks (200 ms) are pre-confirmations inside that block and do not change block.timestamp; block.number is the L2 height and adds nothing beyond the timestamp. The sequencer orders by priority fee (docs), so the launch block is a fee auction that all pays 99 %. T = 4 gives 99 / 12.4 / 0.8 / 0.1 / 0 — coarse but adequate.

Why exponential rather than linear (o1: 99→1 % linear over 20 s; Zora: linear 10 s): the sniper's edge is concentrated in the first block(s) — on an FCFS chain it is latency, on a fee-ordered chain it is the first block's fee auction — so the penalty should be concentrated there too. A linear ramp still charges 50 % at T/2, which mostly taxes humans who react in 1–3 s, delays price discovery (rational traders just wait), and creates a "snipe the ramp" game; the exponential is ~0 by 2 s, is one SHR opcode (no overflow, no fixed-point library), and is the schedule Robinhood volume already accepts (Pons $8.75M fees/24h). The tax buys the launcher ~2–3 s for the disclosed dev buy to be the only cheap fill; after that the curve's own convexity (price already 1.78e-9 after a 0.05 ETH dev buy vs 1.68e-9 at start) is the protection.

Exemption: none by address. The only untaxed buy is the internal dev buy executed inside createToken (call-path exemption, snipeBps = 0 argument to _buy). Since launchedAt is set in the same transaction, every other buy — including any other call in the same block, from the launcher or anyone else — pays the full launch-second tax. This is what makes "no bundles" true by construction rather than by policy.

3.5 Dev buy cap

createToken accepts devBuyEth (msg.value = CREATION_FEE + devBuyEth). The internal buy runs on the fresh curve with snipeBps = 0, tokens go to launcher (not to an arbitrary recipient — the disclosed bag must sit in the launching wallet), and **tokensOut > MAX_DEV_BUY_TOKENS (= 50,000,000e18) ⇒ revertDevBuyExceedsCap(tokensOut)**. On a fresh curve this is deterministic:net = V·cap/(X0−cap)⇒ 0.08842 ETH net, 0.08931 ETH gross at 0 % tax, 0.09116 ETH gross at 2 % tax (V=1.68). Reverting (not clamping) keeps the launch atomic and predictable; the UI shows the cap in ETH.DevBuy(token, launcher, ethIn, tokensOut)` is a dedicated event so indexers can label the bag.

3.6 Sells on the curve

Allowed while status == Trading, same 1 % fee on the ETH output, same creator tax, no snipe tax on sells (a seller cannot "snipe"). Sells revert in Closed/Graduated (Pons: if (graduated || readyToGraduate()) revert CurveGraduated()); they re-open only in WindDown (§5.4).

5. Graduation

5.1 The crossing buy (atomic path)

Inside buy() when out ≥ X_sell − S: 1. Clamp out, compute spent with the exact-out formula (§3.2), refund = received − spent. 2. Effects: R += net, S = X_sell, fees accrued, status = Closed, closedAt = now. Emit Buy, CurveClosed. 3. Interactions: transfer tokens to the buyer; try this.graduate(token) {} catch (bytes reason) { emit GraduationDeferred(token, reason, gasleft()); } — an external self-call so the try/catch boundary is a real call frame; then refund ETH to msg.sender. 4. graduate() (also callable by anyone while status == Closed): status = Graduated (effect first), then EXECUTOR.graduate{value: R}(token, X_res, R) after token.transfer(EXECUTOR, X_res); sets R = 0 for the token. If the executor reverts, the whole graduate() frame reverts, so status stays Closed and the assets stay in the curve — no partial state.

Why try/catch: the crossing buyer must not be denied their fill because pool creation failed; Pons does exactly this (_tryAutoGraduate, comment: "if graduation reverts for any reason … the underlying buy must still succeed, and graduation stays permissionlessly retryable"). 63/64 rule: a buyer can starve the inner call by setting a low gas limit; the catch then emits GraduationDeferred with gasleft() so a keeper/UI notices; the buyer gains nothing (curve closed, nobody can trade until graduate() runs, which anyone can call).

Gas griefing trade-off (who pays the ~0.9M gas): the crossing buyer, as on Pons (measured 952k–986k gas total for the crossing tx) and Bags. At 0.425 gwei that is ≈ 0.0004 ETH ≈ $1 — on Robinhood/GIWA this is not a real grief. The alternative — always two-step with a bounty — would leave every launch untradeable for at least one extra block and needs a funded bounty; rejected. We keep the atomic attempt and the permissionless retry, and the UI's "Graduate now" button for the rare deferred case. Wallets' eth_estimateGas simulates the full path, so the buyer's gas limit normally already includes it.

5.2 Executor (Robinhood: Uniswap v4)

Fixed pool key: currency0 = Currency.wrap(address(0)) (native ETH), currency1 = token, fee = 0, tickSpacing = 200, hooks = LAUNCH_HOOK. Native ETH is address(0) in v4 and always sorts first (initialize reverts if currency0 >= currency1; any token address > 0), so the key never needs sorting logic and the price is always token per ETH (tick ≈ +177k).

Native ETH over WETH (decision D9): Robinhood's WETH 0x0Bd7…AD73 is a 2,202-byte upgradeable aeWETH proxy — an admin could change its semantics, which contradicts the "no admin anywhere" rule for a pool that is supposed to be locked forever; native ETH has no such dependency. v4 supports native settlement (SETTLE with msg.value, SWEEP for change); the curve already holds ETH so no wrap/unwrap gas; Pons V2 pools are (ETH, token) on chain (NEST: currency0 = 0x0), so every Robinhood router/indexer already handles native pairs; and Permit2 is needed only for the token leg. On GIWA the same choice holds for our own pool (component 3) — WETH9 there is an immutable predeploy, but native is still simpler.

Seed computation (the executor knows V, Q at construction; per graduation it receives R and X_res):

tokensFull   = X_res · R / (V + R)           // 204,081,632.65e18 at R = 4.2e18
tokensOver   = X_res − tokensFull            // 81,632,653.06e18
ratioX192    = mulDiv(tokensFull, 2^192, R)  // amount1 / amount0 in Q192 (fits: tokens/ETH ≈ 4.86e7 &lt; 2^64)
sqrtPriceX96 = uint160(sqrt(ratioX192))      // 552,276,925,551,777,206,918,806,258,182,653
tick         = TickMath.getTickAtSqrtPrice(sqrtPriceX96)   // 176,998
tickLowerFull = (MIN_TICK / 200) * 200 = −887,200 ;  tickUpperFull = +887,200
tickUpperOver = floor(tick / 200) * 200 = 176,800   // strictly below current tick ⇒ token-only position
liqFull = LiquidityAmounts.getLiquidityForAmounts(sqrtP, sqrt(tickLowerFull), sqrt(tickUpperFull), R, tokensFull)
liqOver = LiquidityAmounts.getLiquidityForAmount1(sqrt(MIN), sqrt(tickUpperOver), tokensOver)

Orientation check (easy to get backwards): with currency1 = token, price P = token/ETH; a token pump means fewer tokens per ETH ⇒ P falls ⇒ tick decreases. A range entirely below the current tick holds only currency1 (token) and is consumed — converted into ETH that stays in the pool — as the token pumps. So the overhang goes in [MIN_TICK, 176,800] (gap to current price ≤ 200 ticks ≈ 2 %), not above.

Steps in graduate (executor, onlyCurve): 1. POOL_MANAGER.initialize(key, sqrtPriceX96) — no unlock needed (initialize is noDelegateCall only). The hook's beforeInitialize(sender, key, sqrtPriceX96) reverts unless sender == EXECUTOR (the sender passed is msg.sender of initialize, i.e. the executor — Hooks.sol encodes (msg.sender, key, sqrtPriceX96)), so nobody can pre-create our pool key at another price; PoolAlreadyInitialized therefore cannot occur. Belt-and-braces: read slot0 via StateView/extsload and require(sqrtPriceX96Read == sqrtPriceX96). 2. LAUNCH_HOOK.registerPool(key, token, graduatedAt = block.timestamp) — hook stores per-pool token, graduatedAt (for its optional post-graduation snipe window) and reads the creator recipient from the factory registry at claim time (component 2). 3. Token leg approvals: token.approve(PERMIT2, X_res); PERMIT2.approve(token, POSITION_MANAGER, uint160(X_res), uint48(now + 300)) (Pons's _approvePermit2). 4. One POSITION_MANAGER.modifyLiquidities{value: R}(abi.encode(actions, params), now + 300) with actions MINT_POSITION(key, −887200, 887200, liqFull, uint128(R), uint128(tokensFull), LOCKER, ""), MINT_POSITION(key, −887200, 176800, liqOver, 0, uint128(tokensOver), LOCKER, ""), SETTLE_PAIR(ETH, token), SWEEP(ETH, EXECUTOR). The recipient of both mints is the PermanentLocker; PositionManager mints with plain _mint (no onERC721Received callback — Pons documents this), so custody is verified afterwards. 5. positionIdFull = nextTokenId_before, positionIdOverhang = +1; LOCKER.register(token, positionIdFull, positionIdOverhang) which require(ownerOf(id) == LOCKER) for both. 6. Dust: ETH returned by SWEEP (liquidity rounding, a few wei) → CURVE.creditProtocolFees{value}(); token dust left in the executor → LaunchToken(token).burn(dust) (ERC20Burnable). Never revert on dust (Pons: "letting it revert would leave a launch that has already surrendered its reserves unable to ever complete"). 7. Emit Graduated(...) (curve emits with the executor's return values).

Direct PoolManager.unlock callback instead of PositionManager? Cheaper (no NFT, no Permit2, ≈ −100k gas) but the position would be a raw (owner = executor/locker, salt) entry that third-party tooling cannot attribute — the whole Robinhood custody-verification practice (05_lp_burn_signal.md §3 step 2: "v4: PositionManager.ownerOf(tokenId)") keys on the NFT. Pons, Clanker, SPRM all use PositionManager NFTs. We keep the NFT.

Preflight once, not per launch: because V, Q, X0 are immutables, the seed (R ≈ Q, tokensFull, tokensOver) is the same for every launch up to wei-level dust. The executor constructor runs Pons's guard logic on the nominal seed (sqrtPrice strictly inside (MIN_SQRT_PRICE, MAX_SQRT_PRICE); liqFull, liqOver > 0; liq ≤ Pool.tickSpacingToMaxLiquidityPerTick(200) = 3.8e34 — ours is 2.9e22; amounts &lt; 2^127 — ours ≤ 1e27 ≪ 1.7e38) and reverts deployment otherwise. Per-graduation, only the int128/uint128 casts are re-checked.

5.3 PermanentLocker (interface only — this is the sink)

interface IPermanentLocker {          // no owner, no withdraw, no decreaseLiquidity, no transfer-out, no approve, no ERC-1271
    function register(address token, uint256 positionIdFull, uint256 positionIdOverhang) external; // onlyExecutor; verifies ownerOf
    function onERC721Received(address, address, uint256, bytes calldata) external returns (bytes4);  // only from POSITION_MANAGER

    function isLocked(address token) external view returns (bool);

Two properties that make "permanent" checkable from the ABI: (1) there is no function that calls modifyLiquidities, transferFrom, approve, setApprovalForAll, subscribe, or permit; (2) the locker does not implement ERC-1271, so IERC721Permit_v4.permit can never be signed on its behalf. Because the pool fee is 0 and the hook takes its fee outside the position, the locker never needs a collect path either (Pons's locker: "there is no collectFees() here").

5.4 Non-atomic states and the no-admin escape valve

State machine per token: None → Trading → Closed → Graduated, plus Closed → WindDown. - Closed: no buys, no sells, graduate(token) callable by anyone. Expected duration: 0 (atomic) or until the first keeper/UI call (seconds). - WindDown (defence in depth for the no-admin design): if graduate() has been impossible for WINDDOWN_GRACE = 7 days (the call itself first re-tries graduate in a try/catch and only proceeds if that reverts and now ≥ closedAt + 7 days), sells re-open against the curve's own reserves (R ≈ Q), buys stay closed, so holders can exit along the curve. Pons solves the same case with owner-only rescueSweptGraduation behind a timelock; we cannot, so the valve must be permissionless and must only be reachable when graduation is genuinely broken. Reachability requires a revert from immutable v4 core/periphery or our own executor — i.e. a bug — so it never triggers in normal operation.

5.5 Pool-exists collision and copycat pools

  • Our key (with our hook): protected by the beforeInitialize gate — the pool with our hook can only be initialized by our executor, at our price.
  • Other keys on the same token (no hook, other fees): permissionless and unpreventable (v4 initialize is open to anyone; 05_lp_burn_signal shows VIBES/NEST with 4–30 side pools). They are different pools; routers pick by liquidity. The UI must route by our poolId (Graduated event), never by token pair alone.
  • Hook flags: the hook address must encode exactly the permissions it implements (BEFORE_INITIALIZE_FLAG = 1&lt;&lt;13, AFTER_SWAP_FLAG = 1&lt;&lt;6, AFTER_SWAP_RETURNS_DELTA_FLAG = 1&lt;&lt;2; isValidHookAddress rejects mismatches and requires a static fee or ≥ 1 flag). fee = 0 is a valid static fee. Mining is a CREATE2 salt search (HookMiner), per chain.

5.6 Reentrancy and token handling

  • buy/sell/graduate/windDown/claims share one transient reentrancy lock; the executor is onlyCurve and itself non-reentrant.
  • The only ERC-20 this component touches is LaunchToken (OZ: reverts on failure, returns true), and we still use SafeERC20 (safeTransfer, forceApprove) so a future quote-token variant needs no rewrite. No fee-on-transfer or non-returning tokens can enter: v1 supports native ETH only (no USDG/stock pairs — §8).
  • ETH out (refund, sell proceeds, claims) uses call{value} after all effects; failure reverts the trade (EthTransferFailed) — a contract buyer with a reverting receive() can only hurt itself. The dev buy sends tokens to launcher and never sends ETH back except the crossing-refund case, which cannot happen for a capped dev buy.
  • The curve calls out to exactly two trusted contracts (token, executor) plus ETH sends; the executor calls PoolManager/PositionManager/Permit2/hook/locker. The v4 unlockCallback lands on PositionManager, not on us.

7. Cross-component interfaces this design assumes

interface IGraduationExecutor {           // one implementation per chain
    function graduate(address token, uint256 tokensTotal, uint256 ethAmount) external payable
        returns (bytes32 poolId, uint256 positionIdFull, uint256 positionIdOverhang,
                 uint256 tokensSeeded, uint256 tokensOverhang, uint160 sqrtPriceX96, int24 tick);
    // preconditions: msg.sender == CURVE; token.balanceOf(this) ≥ tokensTotal; msg.value == ethAmount
}
interface ILaunchHookRegistrar {          // component 2 (Robinhood only)
    function registerPool(PoolKey calldata key, address token, uint64 graduatedAt) external; // onlyExecutor
}
interface ILaunchRegistry {               // implemented by LaunchFactory, read by hook/UI
    function creatorRecipient(address token) external view returns (address);
    function isLaunchToken(address token) external view returns (bool);
}

The GIWA executor (component 3) implements the same IGraduationExecutor against the minimal native pool; the curve and factory bytecode are chain-agnostic except for the IClock immutable.

8. Open questions for the owner

  1. Overhang disposition (D11): single-sided locked position (chosen: "100 % in the pool", adds ~40 % ask-side depth in the first 2 % above graduation, converting into permanent ETH depth as price rises) vs burn (simplest, supply becomes 918.37M, no ask overhang, but breaks the "exactly 1e9" narrative) vs Pons-style idle lock (weakest). This is a compile-time constant; decide before audit.
  2. Snipe window: Robinhood T = 3 s with sub-second interpolation, GIWA T = 4 s coarse — or the same T on both for a simpler story?
  3. Creator-tax scope: curve only (chosen, = Pons) or also inside the v4 hook (would need the hook to read creatorTaxBps per pool and stack it on the 1 %)?
  4. Recipient timelock proposer: current recipient only (chosen) or launcher OR recipient? And should the pending change be cancellable by anyone holding ≥ x % of supply (a CTO-like path without an admin)?
  5. Quote assets: v1 = native ETH only. Pons's USDG and stock-token pairs produced 3 of its 5 largest tokens this week (01 §3). Adding ERC-20 quotes touches the curve (fee-on-transfer/decimals), the executor (currency ordering becomes data-dependent, Permit2 on both legs) and the hook; propose v1.1.
  6. WindDown valve (§5.4): keep (holder protection with no admin) or drop (one more state to audit)?
  7. Metadata: event-only (chosen) vs a bytes32 metadataHash slot in the registry for on-chain provenance (+22k gas per launch).
  8. Dev-buy recipient: hard-wired to the launching wallet (chosen; the disclosed bag is where the market expects it) vs creatorRecipient.

9. Risks

  • Singleton ETH pooling: an accounting bug affects every live curve at once; mitigated by per-token bounded payouts and the balance invariant, but it must be a first-class invariant test and audit focus.
  • CreateX guard mirroring: predictTokenAddress re-implements CreateX's _guard; a mismatch would only mispredict (deploy still lands where CreateX says), but the UI/cross-chain story depends on it — verify against the deployed CreateX bytecode's source on both chains.
  • Hook address mining per chain: the beforeInitialize gate is what protects the initialize race; a hook deployed with wrong flag bits makes initialize revert forever (HookAddressNotValid) → every graduation deferred → WindDown. Deployment script must assert isValidHookAddress and run one full graduation on testnet (46630 / 91342) before mainnet.
  • Nitro timestamp drift: block.timestamp may lag real time (sequencer clock, bounded −24 h/+1 h); a stalled sequencer clock would keep the snipe tax at 99 % longer than intended — safe direction. The arbBlockNumber interpolation can only reduce tax within the current second, never below the timestamp schedule.
  • GIWA mainnet parameters are guesses until the chain exists (Q = 1.5 assumes day-1 ETH scarcity); the immutables can only be changed by redeploying the curve (new factory) — a v1 GIWA deployment should wait for the chain's gas/ETH reality if that is at all possible.
  • Modified Universal Router on Robinhood (Bags docs: extra minHopPriceX36 field) — trading UI routing for the graduated pool needs its own testing; not this component, but graduation success is only useful if swaps route.
  • No admin means no kill switch for a discovered curve bug: the only lever is to stop advertising the factory and deploy v2 at a new address; tokens already created keep trading on the old singleton.
  • 1-s timestamp granularity on GIWA plus fee-ordered inclusion: the whole first block is a priority-fee auction at 99 % tax — bots may still bid for t = 1 at 12.4 %; if that proves insufficient, T or H can only change via redeploy.
