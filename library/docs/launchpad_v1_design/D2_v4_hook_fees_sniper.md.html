D2 — MemeHook: the Uniswap v4 hook that makes the graduated pool pay the creator (Robinhood Chain)

Design v1 · 2026-09-06 KST · component 2 of launchpad v1 · design only, nothing here deploys anything.

Scope: the singleton v4 hook attached to every graduated pool on Robinhood Chain (chain 4663, canonical PoolManager 0x8366a39CC670B4001A1121B8F6A443A643e40951), the fee escrow it pays into, the post-graduation sniper fee, hook-address mining, and the GIWA mirror (fee taken inside our own V2-style pair; component 3 owns that pair). Component 1 owns the curve/factory, component 4 owns the locker; where this document depends on them the dependency is called out.

Owner rules this component must satisfy (fixed): 1% trading fee in the quote currency, split 80% creator / 20% protocol; protocol recipient immutable at deploy; creator recipient changeable only through the escrow's 3-day timelock; optional per-token creator tax ≤ 2%, immutable; no owner, no pause, no upgrade, no fee switch, no exempt list post-graduation; liquidity permanently locked; sniper tax 99%→~0 over a few seconds, "optionally for the first seconds after graduation".

Sources are cited inline. Primary code was read from Uniswap/v4-core@main (src/libraries/Hooks.sol, LPFeeLibrary.sol, Pool.sol, PoolManager.sol, licenses/BUSL_LICENSE), Uniswap/v4-periphery@main (test/shared/HookMiner.sol, HookMinerCreate3.sol, LICENSE), the Uniswap docs (developers.uniswap.org/llms.mdx/docs/protocols/v4/…), the CreateX README, Arbitrum and GIWA docs, and the verified PonsV2MemeHook / PonsV2FeeEscrow sources on Robinhood Blockscout (scratchpad launch/sc_0xE5e7…e044.json, sc_0xd3AF…Ac9e.json) plus ClankerHookV2.sol (launch/hookv2.sol).

0. Decisions in one screen

# Question Decision Why (short)
D2-1 Where is the 1% taken? beforeSwap + beforeSwapReturnDelta when the quote is the specified currency; afterSwap + afterSwapReturnDelta when the quote is the unspecified currency. Fee is always in quote, never in the memecoin. Pons takes the fee in afterSwap only, so on the most common trade (exact-input ETH buy) its fee lands in the memecoin and needs a trusted feeSweepOperator to convert it. We have no operator, so the fee must be quote-only at the moment it is taken — the Clanker pattern (both callbacks).
D2-2 Pool LP fee Static fee = 0 in the PoolKey (not the dynamic-fee flag). All economics go through the hook; LP fee 0 means no JIT/LP games, exactly 1% total cost for traders, and the locker never needs a fee-collect path.
D2-3 Third-party liquidity Allowed (no beforeAddLiquidity). They earn nothing (LP fee 0); they can remove their own liquidity. Cannot be blocked reliably anyway (the hook only sees the PositionManager as sender); with LP fee 0 there is no incentive to farm; UI shows the locker's position separately from total TVL.
D2-4 beforeRemoveLiquidity Implemented, defence-in-depth only: reverts a liquidity decrease of the registered locked position (sender == PositionManager && params.salt == bytes32(lockedTokenId) && liquidityDelta &lt; 0). The locker (component 4) is the real lock; this makes the "no withdraw path" claim verifiable from the hook too, at the cost of one permission bit.
D2-5 Fee settlement Per swap: poolManager.take(quote, hook, fee) → FeeEscrow.accrue{value}(token, sharedFee, creatorOnlyFee). No ERC-6909 batching, no sweep step, no internal swaps, no unlockCallback. Operator-less and O(1). Cost ≈ 40–50k gas per swap on top of the swap (≈ $0.1 at ~1 gwei). ERC-6909 accrual + permissionless flush is the documented optimisation if gas ever matters.
D2-6 Split Escrow does 80/20 at accrual; creator tax (if any) 100% to creator; protocol recipient immutable; creator recipient per token address with a 3-day timelock. Pull claims, O(1). Owner rule. Keying by token address makes the same config valid on GIWA.
D2-7 Post-graduation sniper fee Yes, buy-side only, integer-second table SNIPE_BPS = [9800, 2400, 200] for elapsed seconds 0/1/2 after initialize, 0 afterwards; total fee capped at 9,900 bps so a buyer always receives ≥ 1%. Proceeds go through the same 80/20 split. No exemptions. Graduation is a public, predictable event and the first pool blocks are a pure latency race on an FCFS sequencer; a 3-second 98%→24%→2% staircase removes the prize. Sells are never taxed above 1%.
D2-8 Hook address Mined for flags 0x22CC (beforeInitialize, beforeRemoveLiquidity, beforeSwap, afterSwap, beforeSwapReturnDelta, afterSwapReturnDelta) and deployed through CreateX deployCreate2 with a permissioned salt; escrow and factory deployed via CreateX deployCreate3 (permissioned salt, no cross-chain byte) so their addresses are known before the hook is mined. Only Robinhood has v4, so cross-chain determinism of the hook is not a goal; the escrow address is the same on both chains. Breaks the hook↔factory↔escrow constructor cycle without any one-shot set* function.
D2-9 Immutability Hook has no owner and no setters. Per-pool terms are written once by the factory in register() and checked in beforeInitialize. Recipients are not stored in the hook at all. Owner rule; also shrinks the audit surface vs Pons (9 onlyOwner setters, rescuePoolFees, operator).
D2-10 Parallel pools for the same token Cannot be prevented on-chain; mitigated by depth (100% of graduation liquidity sits in the hooked pool), a PoolRegistered(token, poolId) event/registry, and the UI routing only to the canonical pool. v4 lets anyone initialise any PoolKey. Copycat pools are already common on Robinhood (VIBES 1 v3 + 4 v4, NEST 30 pairs — docs/launch_research_2026-09-06/05_lp_burn_signal.md §1.3).
D2-11 Quote currency Native ETH (Currency.wrap(address(0))) for the ETH pair; hook is currency-agnostic (USDG/stock pairs possible later) but reverts on inexact receipt (no fee-on-transfer quotes). Avoids depending on the upgradeable aeWETH proxy in the fee path; matches Pons/pools.trade; fees arrive as raw ETH via take.
D2-12 GIWA mirror Same numbers inside the V2-style pair: 1% of gross quote on both directions, same snipe table, same escrow contract at the same address keyed by token. Identical creator economics on both chains without v4.

1. Why beforeSwap + afterSwap (and not one of them)

1.1 The v4 facts that force the design

  • A swap specifies one currency (amountSpecified &lt; 0 = exact input of the input currency; > 0 = exact output of the output currency). The other currency is "unspecified". The quote (ETH) is therefore specified on exact-input buys and exact-output sells, and unspecified on exact-output buys and exact-input sells.
  • beforeSwap may return a BeforeSwapDelta(specifiedDelta, unspecifiedDelta); the PoolManager applies the specified part before the swap: amountToSwap += hookDeltaSpecified, reverting HookDeltaExceedsSwapAmount if the sign flips (Hooks.sol beforeSwap, quoted verbatim in §4). Any unspecified part returned here is only merged into the hook delta after the swap.
  • afterSwap may return an int128 that is added to hookDeltaUnspecified; the PoolManager then builds hookDelta on (specified, unspecified) according to direction and does swapDelta = swapDelta - hookDelta; the hook is credited hookDelta via _accountPoolBalanceDelta(key, hookDelta, address(key.hooks)) (PoolManager.swap).
  • So: a hook that wants the fee always in the quote needs beforeSwap (quote specified) and afterSwap (quote unspecified). A hook that only has afterSwap (Pons) takes the fee in whatever is unspecified — on an exact-input ETH buy that is the memecoin. Pons' verified source says exactly this: "If either cut lands in the memecoin, it is left untouched here and only converted to the quote currency later, in a batched sweepPoolFees call" — gated to feeSweepOperator because the conversion is price-sensitive. Clanker takes the fee in both callbacks and never holds the memecoin (ClankerHookV2._beforeSwap / _afterSwap, four cases).
  • Docs (custom-accounting guide): "exactIn → unspecified = output token → take the fee in output; user receives less output. exactOut → unspecified = input token → take the fee in input; user must pay more input." and for beforeSwap: the returned delta "will be added to the hook's delta and subtracted from the swap delta". Source: http://developers.uniswap.org/llms.mdx/docs/protocols/v4/guides/custom-accounting

1.2 Comparison

Option Fee currency Needs operator / internal swap Extra permission bits Verdict
afterSwap only (Pons) unspecified → memecoin on exact-in buys yes (conversion) 2 rejected: needs a trusted sweeper
beforeSwap only specified → memecoin on exact-out buys and exact-in sells yes 2 rejected, same reason
both, quote-side selection (Clanker) always quote no 4 adopted

2. Hook interface, permissions, storage, events

2.1 Permission table

Flag values from v4-core/src/libraries/Hooks.sol (ALL_HOOK_MASK = (1 &lt;&lt; 14) - 1):

Permission Bit Value MemeHook Used for
beforeInitialize 13 0x2000 yes only the factory may initialise, and only a registered key
afterInitialize 12 0x1000 no (init timestamp is recorded in beforeInitialize)
beforeAddLiquidity 11 0x0800 no third-party liquidity allowed
afterAddLiquidity 10 0x0400 no
beforeRemoveLiquidity 9 0x0200 yes refuse decreases of the locked position (defence-in-depth)
afterRemoveLiquidity 8 0x0100 no
beforeSwap 7 0x0080 yes fee when quote is specified; snipe fee schedule
afterSwap 6 0x0040 yes fee when quote is unspecified
beforeDonate 5 0x0020 no donations only enrich in-range liquidity; harmless
afterDonate 4 0x0010 no
beforeSwapReturnDelta 3 0x0008 yes
afterSwapReturnDelta 2 0x0004 yes
afterAddLiquidityReturnDelta 1 0x0002 no
afterRemoveLiquidityReturnDelta 0 0x0001 no

Required low 14 bits of the hook address: 0x2000|0x0200|0x0080|0x0040|0x0008|0x0004 = 0x22CC (binary 10 0010 1100 1100). Hooks.isValidHookAddress additionally requires that return-delta flags come with their action flags (they do) and, because key.fee = 0 is static, that the hook has at least one flag (it has six). BaseHook's constructor calls Hooks.validateHookPermissions, so a wrongly mined address cannot even deploy. (Docs: "A hook contract must be deployed to an address whose low bits encode exactly the permissions it implements" — http://developers.uniswap.org/llms.mdx/docs/protocols/v4/concepts/hooks.)

Dropping beforeRemoveLiquidity (if component 4 prefers the locker to be the single source of truth) changes the flags to 0x20CC; nothing else in this document changes.

2.2 Interface

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.26;   // evm_version cancun (transient storage is used by PoolManager, not by us)

interface IMemeHook {
    struct PoolTerms {
        address token;            // the launched memecoin (18 dec, 1e9 fixed supply, no FoT)
        bool    tokenIsCurrency0; // derived from key
        uint16  creatorTaxBps;    // 0..200, snapshotted from the launch config; 100% to creator
        uint40  initTimestamp;    // block.timestamp at beforeInitialize; snipe clock
        uint256 lockedTokenId;    // PositionManager tokenId held by the Locker (0 until set)
    }

    // --- factory-only, each callable exactly once per pool -------------------
    function register(PoolKey calldata key, address token, uint16 creatorTaxBps) external; // before poolManager.initialize
    function setLockedPosition(PoolId id, uint256 tokenId) external;                        // after the locker minted

    // --- views ----------------------------------------------------------------
    function terms(PoolId id) external view returns (PoolTerms memory);
    function poolOf(address token) external view returns (PoolId);          // one hooked pool per token, forever
    function feeBpsNow(PoolId id, bool isBuy) external view returns (uint256); // 100 + tax + snipe(t)
    function quoteFee(PoolId id, bool isBuy, bool exactIn, uint256 amount) external view returns (uint256 fee);

    // --- constants (immutables) ------------------------------------------------
    function FACTORY() external view returns (address);
    function ESCROW() external view returns (IFeeEscrow);
    function POSITION_MANAGER() external view returns (address);
    function BASE_FEE_BPS() external pure returns (uint16);   // 100
    function MAX_TAX_BPS() external pure returns (uint16);    // 200
    function MAX_TOTAL_BPS() external pure returns (uint16);  // 9_900
    function SNIPE_SECONDS() external pure returns (uint8);   // 3
}

Everything is immutable or write-once. There is no Ownable, no IUnlockCallback (the hook never opens an unlock of its own — it never swaps), no receive() beyond what take of native ETH needs, and no token-sweep function (a stray token sent to the hook is simply lost; the hook never holds fee balances between transactions).

2.3 Storage

mapping(PoolId => PoolTerms) internal _terms;   // 2 slots per pool (token+bool+tax+ts pack into one; tokenId in the next)
mapping(address => PoolId)   internal _poolOf;  // token → canonical pool; non-zero ⇒ registered

That is the entire state. No pending balances (fees leave the hook in the same call), no recipients (escrow), no policy variables (constants).

2.4 Events

event PoolRegistered(address indexed token, PoolId indexed poolId, Currency quote, bool tokenIsCurrency0, uint16 creatorTaxBps);
event PoolInitialized(PoolId indexed poolId, uint40 initTimestamp, uint160 sqrtPriceX96);

FeeTaken is the indexer's source of truth for creator revenue; grossQuote is defined in §3.1 so that baseFee == grossQuote / 100 always holds.

2.5 Escrow interface (the part the hook depends on)

interface IFeeEscrow {
    // hook (Robinhood) or pair (GIWA) → escrow. `sharedFee` splits 80/20, `creatorOnlyFee` goes 100% to creator.
    function accrue(address token, uint256 sharedFee, uint256 creatorOnlyFee) external payable; // msg.value for native quote
    function quoteOf(address token) external view returns (Currency);
    // claims (pull, O(1))
    function claimCreator(address token) external;
    function claimProtocol(Currency quote) external;
    // 3-day timelock on the creator recipient (owner rule)
    function queueCreatorRecipient(address token, address newRecipient) external;  // by current recipient
    function executeCreatorRecipient(address token) external;                     // after 3 days
    function cancelCreatorRecipient(address token) external;                      // by current recipient
}

Accrual accounting in the escrow: creatorClaimable[token] += 0.8·shared + creatorOnly, protocolClaimable[quote] += shared − 0.8·shared (rounding goes to the protocol). Both are single SSTOREs; claims zero one slot and transfer. The protocol recipient is an immutable. accrue is restricted to the hook (immutable) and, for the curve phase, to the token's registered curve (component 1 registers curveOf[token] when it launches — the escrow's FACTORY is immutable too). This mirrors Pons' PonsV2FeeEscrow ("Both the bonding curve and the post-graduation PonsV2MemeHook credit the same way, so a recipient's balance is denominated identically before and after graduation") minus its permissionless credit (we do not want third parties inflating balances).

3. Exact fee accounting

3.1 Definition of the fee

Let p = feeBps/10_000 (normally 0.01; more during the snipe window; plus tax). Define gross quote G as the quote amount on the paying side of the trade — what the swapper pays on a buy, what the pool pays on a sell. The fee is always p·G:

Case Specified Where taken Known amount G fee Delta returned
A. exact-in buy (ETH in, token out) quote (input) beforeSwap X = -amountSpecified X X·p BeforeSwapDelta(+fee, 0)
B. exact-out buy (token out exact) token (output) afterSwap pool took Q = -delta.quote Q/(1-p) Q·p/(1-p) (round up) int128(+fee)
C. exact-in sell (token in, ETH out) token (input) afterSwap pool gave Y = +delta.quote Y Y·p int128(+fee)
D. exact-out sell (ETH out exact) quote (output) beforeSwap S = amountSpecified S/(1-p) S·p/(1-p) (round up) BeforeSwapDelta(+fee, 0)

Why this normalisation: cases A and C are the natural "1% of what crosses the boundary"; B and D are the same trades expressed exact-out, and dividing by (1−p) makes the fee identical to what the exact-in form would have charged for the same fill (Clanker uses the same 1/(1−p) correction in its exact-out paired-out case). A trader therefore sees exactly 1% whichever way the router quotes the trade.

3.2 Mechanics per case (using the verbatim PoolManager semantics)

Hooks.beforeSwap (v4-core, quoted): amountToSwap = params.amountSpecified; … hookDeltaSpecified = hookReturn.getSpecifiedDelta(); if (hookDeltaSpecified != 0) { bool exactInput = amountToSwap &lt; 0; amountToSwap += hookDeltaSpecified; if (exactInput ? amountToSwap > 0 : amountToSwap &lt; 0) HookDeltaExceedsSwapAmount…revert }.

Hooks.afterSwap (quoted): hookDeltaUnspecified += callHookWithReturnDelta(...).toInt128(); … hookDelta = (params.amountSpecified &lt; 0 == params.zeroForOne) ? toBalanceDelta(hookDeltaSpecified, hookDeltaUnspecified) : toBalanceDelta(hookDeltaUnspecified, hookDeltaSpecified); swapDelta = swapDelta - hookDelta;

  • A (exact-in buy, quote specified): amountSpecified = −X. Hook returns (+fee, 0). amountToSwap = −X + fee = −(X−fee): the pool only swaps X−fee. After the swap the PoolManager subtracts hookDelta = (fee on quote) from the swapper's delta → swapper's quote delta is −(X−fee) − fee = −X (pays the full X) and the hook's delta is +fee. The hook takes fee during the callback (transiently −fee, netted to 0 once _accountPoolBalanceDelta credits it; the only invariant is NonzeroDeltaCount == 0 at the end of unlock).
  • D (exact-out sell, quote specified): amountSpecified = +S. Hook returns (+fee, 0). amountToSwap = S + fee = G: the pool pays out G quote and charges tokens for G. Swapper's delta: +G − fee = +S (receives exactly S). Hook: +fee.
  • B (exact-out buy, quote unspecified): the pool's swap already ran; delta.quote = −Q. Hook returns int128(+fee) with fee = ⌈Q·p/(1−p)⌉; swapDelta − hookDelta makes the swapper's quote delta −Q − fee. Hook: +fee.
  • C (exact-in sell, quote unspecified): delta.quote = +Y. Hook returns +fee = Y·p; swapper receives Y − fee. Hook: +fee.

The v4 swap never touches the memecoin side of the hook. The hook's delta after every swap is exactly +fee in quote, consumed by take. No ERC-6909 claim tokens are minted.

3.3 Solidity sketch (core of the hook)

uint16 constant BASE_FEE_BPS = 100;
uint16 constant MAX_TAX_BPS  = 200;
uint16 constant MAX_TOTAL_BPS = 9_900;   // buyer always keeps ≥ 1% — never a 100% fee
uint16[3] constant SNIPE_BPS = [9_800, 2_400, 200]; // elapsed whole seconds 0,1,2 after initialize (buys only)

function _feeBps(PoolTerms memory t, bool isBuy) internal view returns (uint256 bps, uint256 snipe) {
    bps = BASE_FEE_BPS + t.creatorTaxBps;
    if (isBuy) {
        uint256 dt = block.timestamp - t.initTimestamp;      // Arbitrum: sequencer clock, monotonic, 1-second granularity
        if (dt &lt; 3) { snipe = SNIPE_BPS[dt]; if (bps + snipe > MAX_TOTAL_BPS) snipe = MAX_TOTAL_BPS - bps; }
        bps += snipe;
    }
}

function _beforeSwap(address, PoolKey calldata key, SwapParams calldata p, bytes calldata)
    internal override returns (bytes4, BeforeSwapDelta, uint24)
{
    PoolId id = key.toId();
    PoolTerms memory t = _terms[id];
    bool quoteIs0 = !t.tokenIsCurrency0;
    bool isBuy = (p.zeroForOne == quoteIs0);               // quote → token
    bool exactIn = p.amountSpecified &lt; 0;
    if (exactIn != isBuy) return (BaseHook.beforeSwap.selector, BeforeSwapDeltaLibrary.ZERO_DELTA, 0); // quote unspecified → afterSwap
    (uint256 bps, uint256 snipe) = _feeBps(t, isBuy);
    uint256 fee = exactIn
        ? uint256(-p.amountSpecified) * bps / 10_000                                   // A: X·p
        : FullMath.mulDivRoundingUp(uint256(p.amountSpecified), bps, 10_000 - bps);    // D: S·p/(1−p)
    _collect(id, t, quoteIs0 ? key.currency0 : key.currency1, fee, bps, snipe, isBuy, exactIn);
    return (BaseHook.beforeSwap.selector, toBeforeSwapDelta(int128(int256(fee)), 0), 0);
}

function _afterSwap(address, PoolKey calldata key, SwapParams calldata p, BalanceDelta d, bytes calldata)
    internal override returns (bytes4, int128)
{
    PoolId id = key.toId();
    PoolTerms memory t = _terms[id];
    bool quoteIs0 = !t.tokenIsCurrency0;
    bool isBuy = (p.zeroForOne == quoteIs0);
    bool exactIn = p.amountSpecified &lt; 0;
    if (exactIn == isBuy) return (BaseHook.afterSwap.selector, 0);                     // already taken in beforeSwap
    int128 q = quoteIs0 ? d.amount0() : d.amount1();                                   // swapper's quote delta
    (uint256 bps, uint256 snipe) = _feeBps(t, isBuy);
    uint256 fee = isBuy
        ? FullMath.mulDivRoundingUp(uint256(uint128(-q)), bps, 10_000 - bps)           // B: Q·p/(1−p)
        : uint256(uint128(q)) * bps / 10_000;                                          // C: Y·p
    _collect(id, t, quoteIs0 ? key.currency0 : key.currency1, fee, bps, snipe, isBuy, exactIn);
    return (BaseHook.afterSwap.selector, int128(int256(fee)));
}

function _collect(PoolId id, PoolTerms memory t, Currency quote, uint256 fee,
                  uint256 bps, uint256 snipe, bool isBuy, bool exactIn) internal {
    if (fee == 0) return;
    uint256 taxFee   = fee * t.creatorTaxBps / bps;      // proportional slices of the one fee
    uint256 snipeFee = fee * snipe / bps;
    uint256 baseFee  = fee - taxFee - snipeFee;
    if (quote.isAddressZero()) {
        poolManager.take(quote, address(this), fee);                       // ETH lands in the hook…
        ESCROW.accrue{value: fee}(t.token, baseFee + snipeFee, taxFee);    // …and leaves in the same call
    } else {
        uint256 before = IERC20(Currency.unwrap(quote)).balanceOf(address(ESCROW));
        poolManager.take(quote, address(ESCROW), fee);
        if (IERC20(Currency.unwrap(quote)).balanceOf(address(ESCROW)) - before != fee) revert InexactQuote(); // no FoT quotes
        ESCROW.accrue(t.token, baseFee + snipeFee, taxFee);
    }
    emit FeeTaken(id, t.token, isBuy, exactIn, fee * 10_000 / bps, baseFee, snipeFee, taxFee);
}

Notes: take while the hook's delta is not yet credited is allowed — the docs' own fee example does it in beforeSwap; the debt is netted by _accountPoolBalanceDelta after afterSwap. HookDeltaExceedsSwapAmount cannot trigger: for exact-in fee = X·p &lt; X because p ≤ 0.99; for exact-out the specified delta only increases the magnitude. When X·(1−p) rounds to zero the pool swaps 0 and returns early ("when the amount swapped is 0, there is no protocolFee applied" — Pool.sol) — the buyer paid the fee for nothing, which is the intended sniper outcome at t = 0 for dust trades.

3.4 Native ETH vs WETH

  • A v4 native pool uses currency0 = Currency.wrap(address(0)); take of a native currency sends ETH. The hook then forwards it with accrue{value: fee} — two value transfers per swap (~2 × 9k gas incl. the calls). With WETH (0x0Bd7…AD73, an upgradeable aeWETH proxy) the transfers are ERC-20 transfers at similar cost but the fee path would depend on an upgradeable third-party contract. Native ETH is recommended for the ETH pair; Universal Router, Pons and pools.trade already trade native v4 pools on this chain. Escrow claims of native ETH use call{value} with reentrancy guard and checks-effects-interactions.
  • ERC-20 quotes (USDG 0x5fc5…d168, stock tokens) work unchanged, but the exact-receipt check means a quote that takes a transfer fee, rebases, or pauses transfers will make every swap revert — the factory's quote whitelist (component 1) is the control. Pons hit exactly this and added an owner-only rescuePoolFees; we have no owner, so the whitelist must be strict (v1: native ETH only; USDG after verifying its implementation).

3.5 Gas (estimate, to be measured in Foundry)

Baseline v4 swap through Universal Router ≈ 120–150k. Hook adds: two callbacks (~8k), one take + native transfer (~12k), accrue with two warm/cold SSTOREs (~25–30k), event (~2k) ⇒ ≈ 45–55k. At Robinhood's 0.5–1.35 gwei and ETH ≈ $2.5k that is $0.06–0.19 per swap. The ERC-6909 variant (mint claims per swap, flush(token) permissionless) saves ~20k per swap; keep it as a v1.1 option, not in v1.

4. Post-graduation sniper fee — decision: yes, 3 seconds, buy-side, staircase

Reasoning:

  • Graduation is deterministic and observable (the last curve buy crosses the threshold; the pool is created in that same transaction — component 1). Bots watching the curve will submit pool buys the instant the graduation tx is sequenced. With 0.1-s blocks and FCFS ordering the only skill is latency; the prize is a small first-mover edge on a pool that opens at the curve's end price (no discount, unlike a fresh single-sided pool). The fee removes the prize; humans who buy a few seconds later pay 1%.
  • Pons: 99% → 0 exponential, snipeTaxSeconds() = 3 on-chain (docs say 5 s; on-chain governs), proceeds join the fee split; o1: 99% → 1% linear over 20 s, surcharge to platform; Zora: 99% → base over 10 s; Clanker: MEV modules up to 2 minutes with 80% max fee. Three seconds is the shortest in production and enough at 0.1-s blocks (30 blocks).
  • Timestamp source: on Arbitrum "block timestamps … are updated every child chain block based on the sequencer's clock", must be non-decreasing and "within the established boundaries (24 hours earlier than the current time or one hour in the future)"; "timing assumptions … unreliable in the shorter term (minutes)" (https://docs.arbitrum.io/build-decentralized-apps/arbitrum-vs-ethereum/block-numbers-and-time). That warning is about drift relative to L1 time, which we do not care about — we only need "seconds elapsed since the pool's own init timestamp on the same clock", which is monotonic and second-granular. block.number is unusable here (it approximates the L1 block); ArbSys(0x64).arbBlockNumber() would give 0.1-s granularity but adds a precompile dependency and is not portable to GIWA — rejected.
  • Integer-second staircase instead of an exponential: with second granularity a continuous curve is a lie anyway; three constants are auditable and identical on both chains. Chosen table (bps added to the 1% base on buys): t=0 → 9,800 (total 9,900), t=1 → 2,400 (2,500), t=2 → 200 (300), t≥3 → 0 (100). Roughly Pons' "near 25% one second in and around 3% at two seconds".
  • Total is capped at 9,900 bps so a 100% fee (which would make exact-out swaps impossible — Pool.sol reverts InvalidFeeForExactOut for a 100% LP fee, and a 100% hook fee would simply burn the buyer's input) never occurs.
  • No exemptions: the owner's single disclosed dev-buy happens on the curve (component 1) and is already in the wallet at graduation; there is no address list in the hook (Pons allows 32 exempt wallets — a bundling vector we deliberately do not have).
  • Sells: never above 100 + tax bps. A holder can always exit at 1%.
  • Proceeds: same 80/20 split as the base fee (Pons does the same; o1 keeps the surcharge). This is the owner's call; the hook passes snipeFee inside sharedFee so switching it to 100% protocol (or burning it) is a one-line escrow change before deploy.

Turning it off is a compile-time change (SNIPE_BPS = [0,0,0]); v1 ships with it on.

5. Hook address mining and deployment ceremony

5.1 Mining

HookMiner.find(deployer, flags, creationCode, constructorArgs) (v4-periphery test/shared/HookMiner.sol) loops salt = 0 … 160_443 computing keccak256(0xFF ‖ deployer ‖ salt ‖ keccak256(creationCode ‖ args)) until addr & 0x3FFF == flags && addr.code.length == 0. For six flags the expected number of trials is 2¹⁴ = 16,384; the chance of exhausting MAX_LOOP is ≈ e^(−160444/16384) ≈ 5·10⁻⁵ — mine off-chain (Python/Rust) anyway, it is instant.

5.2 Through CreateX (0xba5Ed099633D3B313e4D5F7bdc1305d3c28ba5Ed, present on both chains)

  • deployCreate2(bytes32 salt, bytes initCode): CreateX is the CREATE2 deployer, so deployer = CreateX in the formula, and the salt CreateX actually uses is the guarded salt: "it is essential to provide the guarded salt value, meaning the value after being processed by the _guard function" (README). With the permissioned form (first 20 bytes = our deployer EOA, byte 21 = 0x00) the guarded salt is keccak256(abi.encode(msg.sender, salt)); with byte 21 = 0x01 it is keccak256(abi.encode(msg.sender, block.chainid, salt)). Mining therefore iterates the 11 free entropy bytes of the raw salt and evaluates addr = keccak256(0xFF ‖ CreateX ‖ guardedSalt ‖ initCodeHash). Verify the exact _guard branches against CreateX source before mining (open question OQ-4).
  • Permissioned salt is not strictly needed for CREATE2 (an address is bound to the init-code hash, so a front-runner can only deploy our identical bytecode at our address), but it is free and avoids a stranger burning the address with a different constructor arg set. Use it.
  • initCode includes the constructor args (PoolManager, FACTORY, ESCROW, POSITION_MANAGER), so the mined salt is specific to those addresses. Robinhood testnet (46630) will have different PoolManager/PositionManager addresses ⇒ a different salt ⇒ a different hook address there. Only mainnet needs a "pretty" address; testnet just needs valid flags.

5.3 Breaking the constructor cycle without setters

hook needs FACTORY and ESCROW; factory needs hook and escrow; escrow needs hook and factory. Pons breaks this with setFactory() (one-shot, owner-only). We break it with CREATE3, whose address does not depend on init code ("Any change in the salt value will result in a new destination address" — CreateX README; HookMinerCreate3 in v4-periphery does the same for hooks):

  1. Choose permissioned CREATE3 salts S_escrow, S_factory (first 20 bytes = deployer EOA; byte 21 = 0x00 so the same addresses are reproducible on GIWA). Compute ESCROW = computeCreate3Address(guard(S_escrow)), FACTORY = computeCreate3Address(guard(S_factory)). Permissioned salts are mandatory for CREATE3: the address is independent of bytecode, so an unpermissioned salt would let anyone deploy arbitrary code at our predicted escrow address first.
  2. Mine S_hook for MemeHook(POOL_MANAGER, FACTORY, ESCROW, POSITION_MANAGER) → HOOK (low bits 0x22CC).
  3. deployCreate3(S_escrow, FeeEscrow(HOOK, FACTORY, PROTOCOL_RECIPIENT, WETH?…)), deployCreate3(S_factory, Factory(HOOK, ESCROW, …)), deployCreate2(S_hook, MemeHook(...)). Each constructor asserts the others' addresses have code only where ordering allows (hook last: it can require(FACTORY.code.length > 0 && ESCROW.code.length > 0); escrow/factory cannot check the hook yet — they store the predicted address as immutable; the launch script verifies all three after step 3 and refuses to open launches otherwise).
  4. On GIWA: same S_escrow ⇒ same escrow address; the pair factory replaces the hook (component 3).

No set* functions exist anywhere in the three contracts.

5.4 Reentrancy / unlock semantics

  • All hook callbacks are onlyPoolManager (BaseHook). They run inside the router's unlock; take requires onlyWhenUnlocked, satisfied. The hook never calls unlock itself and never swaps, so Hooks' "if (msg.sender == address(self)) return" bypass (which Pons relies on to make its internal conversion swaps fee-free) is irrelevant to us — and there is no code path by which a fee-free swap through this pool can exist.
  • During _collect the hook makes one external call to the escrow. The escrow does not call back into the PoolManager or the hook; accrue is onlyHook/onlyCurve, non-payable for ERC-20 quotes, and does only arithmetic + SSTORE. Native take to the hook triggers the hook's receive() — a no-op.
  • Escrow claims: nonReentrant, zero the balance before call{value}; ERC-20 claims use safeTransfer. No permissionless credit (unlike Pons), so balances cannot be inflated by outsiders.
  • donate is permissionless on any pool; it can only credit in-range liquidity (the locked position, which has no collect path — donated value is stuck; harmless). The hook reads no balances and no prices, so donate/flash-loan manipulation cannot change any fee.
  • Uniswap governance's protocol fee: Pool.swap applies protocolFee (set by Uniswap's ProtocolFeeController, max 0.1% per direction) in addition to the LP fee, even on lpFee = 0 pools. If Uniswap ever switches it on for this chain, traders pay up to +0.1% to Uniswap; our 1% is unaffected. External, not controllable — disclose in the UI.

5.5 Fee-on-transfer

The launched token has no transfer hook, no tax, no rebase (component 1). The hook never takes the memecoin, so even a hostile token could not break fee collection; only the quote matters (see §3.4). The exact-receipt check reverts the whole swap rather than mis-accounting.

6. Parallel pools, registry, and why the hook cannot "own" the token

  • Anyone can call PoolManager.initialize with any PoolKey for our token — hookless, other hooks, other fee tiers, other quotes. Pools are keyed by the whole PoolKey, so ours (token/ETH, fee 0, tickSpacing 200 (TBD component 1), hooks = MemeHook) is one of possibly many. Observed on Robinhood: VIBES 1 v3 + 4 v4 pools, NEST 30 v4 pairs (docs/launch_research_2026-09-06/05_lp_burn_signal.md §1.3). Nothing at the token level can stop it without transfer restrictions, which the owner rules forbid.
  • What the hook does guarantee: exactly one pool with this hook per token (_poolOf[token] set once by register; beforeInitialize reverts unless sender == FACTORY and the key is registered and not yet initialised), and that pool can never be re-initialised (v4 forbids it).
  • Economic mitigation: 100% of graduation liquidity (all the raised ETH + reserved tokens; component 1) sits in the hooked pool; a parallel hookless pool needs someone to seed both sides at market price and then earns them an LP fee — which becomes rational only for large tokens, exactly where copycat pools appear today. Routers (Universal Router, aggregators, GMGN) split by depth; the leak is bounded by the share of volume the parallel pool can absorb.
  • UI/registry mitigation: the PoolRegistered(token, poolId, …) event is the canonical mapping; the UI, the API and the launch page link only that poolId; the token page shows "canonical pool / other pools" with the locker's position highlighted. This is the same situation every hook launchpad lives with (Pons, Clanker, Zora).

7. MEV on Robinhood's FCFS sequencer (0.1-s blocks)

  • Ordering: "Transactions are ordered by the order in which they are received" (default FCFS); chains "can override this default … with Timeboost, which auctions an 'express lane'"; non-express transactions then get "a default 200-millisecond artificial delay" (https://docs.arbitrum.io/how-arbitrum-works/sequencer, …/timeboost/gentle-introduction). Whether Robinhood Chain has enabled Timeboost is not verified (OQ-1); the chain docs site refused TLS from here.
  • Sandwich profile: there is no public mempool to read pending swaps from — third parties see a transaction only once the sequencer has ordered it. Classical sandwiching (front-run + back-run around a pending victim) is therefore unavailable to outsiders; only the sequencer operator could do it, which is an honesty assumption we share with every venue on the chain. What remains: (a) back-running (arbitrage after a large buy) — harmless to the trader, and with LP fee 0 the arb's cost is our 1% both ways, so small imbalances persist rather than being arbed; (b) latency races to be first after a public event — graduation (handled by §4), and any predictable large buy such as a public "buy at 12:00" — nothing on-chain can fix that; (c) with Timeboost, an express-lane holder gets a 200-ms head start on events, not on other users' pending transactions — it would sharpen (b) but does not create sandwiches.
  • Hook-specific: fees are pure functions of (amount, direction, timestamp); no oracle, no TWAP, no balance reads ⇒ no manipulation surface. Slippage protection remains the router's amountOutMinimum as usual.
  • GIWA (OP Stack): "The Sequencer executes transactions from the mempool in priority fee order (highest fee first)" and "OP Stack chains do not have a public mempool" (https://docs.optimism.io/stack/differences). Flashblocks give "preconfirmation … (최대 200ms)" but "are not about creating blocks faster" (https://docs.giwa.io/network-information/flashblocks.md). Consequence: the post-graduation race on GIWA is a priority-fee auction within the first 1-s block rather than a latency race; the same 3-second staircase applies (the whole first block is t = 0 or t = 1), and outsiders still cannot sandwich.

8. Swap walk-through with numbers

Assumptions (component 1's numbers are not final; these mirror the Pons V2 graduation observed on-chain so they are realistic): graduation deposits 4.2 ETH + 204,081,633 tokens into a full-range fee-0 pool at the curve's end price P₀ = 4.2 / 204.08M = 2.058e-8 ETH/token (FDV ≈ 20.6 ETH ≈ $51k at $2,476/ETH). Full-range v4 liquidity behaves as x·y = k with k = 4.2 × 204,081,633 = 8.5714e8.

8.1 Case A — exact-input 1 ETH buy, 10 seconds after graduation (snipe over)

  1. Router calls swap(key, {zeroForOne: true (ETH is currency0), amountSpecified: −1e18, limit}).
  2. beforeSwap: quote specified, isBuy, bps = 100, fee = 1e18 × 100 / 10 000 = 0.01 ETH. Hook takes 0.01 ETH and calls accrue{value: 0.01}(token, 0.01, 0). Returns BeforeSwapDelta(+0.01e18, 0). amountToSwap = −0.99e18.
  3. Pool swap with LP fee 0: tokens out = y − k/(x + 0.99) = 204,081,633 − 8.5714e8 / 5.19 = 204,081,633 − 165,152,767 = 38,928,866 tokens (3.89% of supply). New reserves 5.19 ETH / 165.15M tokens; new spot 3.143e-8 (+52.7%); effective price paid 1 / 38.93M = 2.569e-8 (24.8% worse than spot, of which 1% is fee).
  4. afterSwap: quote was specified → returns 0.
  5. PoolManager: swapDelta = (−0.99e18, +38,928,866e18) − hookDelta(+0.01e18, 0) = (−1.00e18, +38,928,866e18). Hook delta: +0.01e18 − 0.01e18 (take) = 0. Router settles 1 ETH, takes the tokens.
  6. Escrow: creatorClaimable[token] += 0.008 ETH, protocolClaimable[ETH] += 0.002 ETH. FeeTaken(poolId, token, isBuy=true, exactIn=true, gross=1e18, base=0.01e18, snipe=0, tax=0).

8.2 Same 1 ETH buy, 1 second after graduation (snipe tier 1)

bps = 100 + 2,400 = 2,500 → fee 0.25 ETH (0.20 creator / 0.05 protocol); pool receives 0.75 ETH → tokens out = 204,081,633 × 0.75 / 4.95 = 30,921,460. At t = 0 the fee is 0.99 ETH and the buyer gets 204,081,633 × 0.01 / 4.21 = 484,754 tokens for 1 ETH — the sniper's expected edge is gone.

8.3 Case C — the buyer of 8.1 sells everything back (exact-input 38,928,866 tokens)

Pool gives Y = x − k/(y + 38,928,866) = 5.19 − 8.5714e8/204,081,633 = 5.19 − 4.2 = 0.99 ETH. afterSwap: q = +0.99e18, fee = 0.0099 ETH, returns +0.0099e18; swapper receives 0.9801 ETH. Round trip cost 1.99% = two 1% fees, zero LP fee, zero price drift. Creator earns 0.008 + 0.00792 = 0.01592 ETH on the round trip.

8.4 Case B — exact-output buy of exactly 10,000,000 tokens from the graduation state

Pool needs Q = k/(y − 1e7) − x = 8.5714e8 / 194,081,633 − 4.2 = 0.216404 ETH. afterSwap: fee = ⌈0.216404 × 100 / 9 900⌉ = 0.0021859 ETH; swapper pays 0.218590 ETH, of which the fee is exactly 1.000%.

8.5 Case D — exact-output sell for exactly 0.5 ETH

beforeSwap: fee = ⌈0.5 × 100 / 9 900⌉ = 0.0050505 ETH; amountToSwap = 0.5050505 ETH leaves the pool; the swapper receives 0.5 ETH and pays tokens for 0.5050505 ETH — again fee = 1% of the gross quote leaving the pool.

9. GIWA mirror (brief; component 3 owns the pair)

  • No Uniswap on GIWA (v4-core BUSL until 2027-06-15; no v2/v3 deployment either), so component 3 ships a minimal constant-product pair: no LP token, no burn, no skim, mint only by the factory at graduation, sync only for donations, liquidity permanent by construction.
  • Fee inside swap(amountOut…): on a buy (ETH/WETH in) the pair computes fee = amountIn × bps / 10 000 first, forwards it to the escrow, and checks the invariant on amountIn − fee; on a sell it computes amountOut from x·y = k, forwards amountOut × bps / 10 000 to the escrow and pays the rest. Exact-output paths use the same 1/(1−p) normalisation as §3.1 so quotes match Robinhood. Snipe table identical (block.timestamp − createdAt, 1-s blocks: tier 0 is the graduation block, tier 1 the next).
  • Quote on GIWA: WETH9 predeploy 0x4200…0006 (not upgradeable, unlike Robinhood's aeWETH) or native ETH via a thin wrapper in the pair — component 3's call; the escrow accepts both (quoteOf[token]).
  • Escrow: same bytecode, same CREATE3 salt, same address on GIWA (Sepolia 91342 today; mainnet 9134 reserved); accrue callers are the pair factory's pairs instead of the hook; creator recipient/timelock state is per chain (no bridging), but keyed by the same token address so the UI can show one config.
  • GIWA sequencer context in §7.

11. Risks

  1. Parallel hookless pool for a big token drains fee volume (bounded by routing; cannot be prevented on-chain).
  2. Uniswap protocol fee switch (≤ 0.1%/direction) can be enabled by Uniswap governance on any pool — traders pay more, creator unaffected.
  3. Quote token hazards (ERC-20 quotes only): pausable/FoT/rebasing quote ⇒ every swap reverts, no rescue path by design. v1: native ETH only.
  4. Timestamp staircase edge: the graduation block and the next ~9 blocks share t = 0; a human who buys in the same second as graduation pays 99%. UI must block buys until t ≥ 3 and show the countdown.
  5. Timeboost on Robinhood (unverified): would give an express-lane holder a 200-ms head start on graduation snipes; the staircase still makes t = 0 unprofitable.
  6. CreateX guard formula / CREATE3 front-running: a mistake in the salt guard mis-predicts the escrow address; an unpermissioned CREATE3 salt lets a stranger squat the address. Mitigation: permissioned salts, dry-run on testnet 46630, code.length assertions in the hook constructor.
  7. No rescue at all: any bug in accrue bricks swaps on every pool of this hook forever (there is no upgrade). Mitigation: minimal surface (≈150 lines of hook logic), Foundry invariant tests against the real v4 bytecode, and a factory that can be retired by deploying a new hook+factory+escrow trio for future launches (existing pools keep the old hook).
  8. Licence (low): hook compiles against BUSL-licensed v4-core libraries; use is the documented, intended one; GIWA avoids core entirely.
