GIWA Simple Open DEX: fee와 organic volume을 함께 만드는 조건

기준일: 2026-09-03 KST
연구 모드: Insane Research strict
경계: research_only=true, strategy_consumption_allowed=false, order_input=false

이 보고서는 기술·사업·규제 리서치이며 법률·세무·투자 자문이 아니다. 상대적 위험 등급은 적법 확인이나 인허가 면제를 뜻하지 않는다. 배포, 서명, 거래, 유동성 공급, 토큰 발행·판매와 외부 프로젝트 접촉은 수행하지 않았다.

1. 판단 요약

1.1 가장 맞는 제품

사용자의 Solana 밈, Solana DEX utility, 생태계 기여 경험을 합치면 가장 맞는 제품은 독립 브랜드의 최소형 v3-compatible GIWA liquidity venue다.

  • trader 화면은 v2처럼 단순하게 만든다.
  • core는 희소한 자본을 실제 거래 가격대에 집중시킬 수 있는 concentrated-liquidity 구조를 우선 검토한다.
  • pool·fee tier 수를 제한하고, vault·keeper·farm·referral·launchpad·bridge를 빼서 attack surface를 줄인다.
  • team protocol/interface fee는 초기 0으로 두고, 고정 B2B fee와 조건부 own-capital LP fee를 수익의 첫 단계로 삼는다.
  • GIWA·Uniswap 양쪽과 canonical deployment를 논의하되, 공식 venue가 wallet·API· liquidity까지 갖추면 같은 페어로 싸우지 않고 integration·LP route로 전환한다.

(src_211, src_218~src_227, src_230~src_231; clm_309~clm_312, clm_330)

1.2 지금은 배포할 때가 아니다

2026-09-03 현재 공식 문서는 public mainnet과 GIWA Wallet을 개발 중으로 표시한다. 공개 테스트망은 GIWA Sepolia, chain ID 91342, ETH gas이며 public RPC는 production 용도가 아니다. Circle의 issuer registry에는 GIWA USDC가 없고 LI.FI와 OpenOcean의 현재 지원 표면에도 GIWA route가 없다. 따라서 “접속 가능한 테스트넷”은 있지만 검증 가능한 real-value order flow는 아직 없다. 이것은 접근 불가가 아니라 생산 유통 전제의 부재에 관한 판단이다. (src_201~src_205, src_209, src_215~src_217; clm_301~clm_303)

1.3 거래량에 대한 정직한 전제

거래량은 UI가 아니라 자산 수요, 유동성 깊이, 실행 가격과 유통 경로의 결과다.

canonical asset
      ↓
anchor-pair depth
      ↓
best net execution
      ↓
wallet / partner / aggregator routing
      ↓
independent repeat flow
      ↓
fees and retained liquidity

어느 한 고리가 끊기면 화면을 아무리 단순하게 만들어도 volume은 생기지 않는다. 반대로 UI는 단순해도 위 고리가 연결되면 주문이 올 수 있다. (src_208, src_215~src_217, src_227~src_233; clm_313~clm_316)

2. 네 가지 목표가 충돌하는 지점

우리가 원하는 네 가지는 동시에 최대화되지 않는다.

목표 원하는 것 충돌하는 것
Simple 작은 code·UI surface CLMM position 관리, routing과 안전 고지는 복잡함
Volume 깊은 liquidity와 distribution own fork는 liquidity를 쪼개고 incentive는 비용을 만듦
Fee 거래에 비례하는 team revenue 한국 VASP·중개·영업성 및 이해상충 위험
Decentralized permissionless·non-custodial hosted UI, admin key와 GIWA sequencer trust layer는 별도

따라서 우선순위를 정해야 한다. 이 보고서는 체결 품질과 법적 생존성을 1순위, 단순 UI를 2순위, team direct take rate를 마지막으로 둔다. direct fee를 먼저 켰다가 order flow도 없고 규제 위험만 생기는 구성이 가장 나쁘다. (src_204, src_206, src_234~src_244; clm_319~clm_325, clm_332)

GIWA Sepolia에서는 다음을 직접 확인했다.

test token은 경제적 가치가 없고 testnet은 변경·중단될 수 있다. 그러므로 “첫 GIWA 스왑”이라는 positioning은 이미 성립하지 않고, test transaction 수나 화면상 USD 숫자를 adoption으로 부르면 안 된다. 차별화는 depth, partner routing, verified asset, audit와 fee transparency여야 한다. (src_209, src_211~src_214; clm_304)

3.3 며칠 전 프로젝트 발표의 사용법

GASOK 공식 페이지는 Phase 3를 2026년 8~9월 test metric과 private-mainnet 작업으로 설명하고, GIWA Wallet 노출도 ‘기회’로 표현한다. Upbit 거래지원과도 무관하다. 이름별 공개 표는 공식 roster가 아니라 프로젝트 자기발표와 커뮤니티 집계다. 따라서 그 목록은 partnership lead로만 쓰고 선정·상장·실사용 보장으로 쓰지 않는다. (src_208, src_210; clm_305)

4. 권고 DEX 구조

4.1 선택지 비교

선택지 자본 효율 운영 복잡도 order-flow 전망 team fee 통제 판단
v2-style own fork 낮음 낮음 깊은 seed capital 없으면 약함 높음 test·비상안
최소 v3-compatible own venue 높음, range 내 중간~높음 scarce capital에 가장 유리 높음 조건부 기본안
canonical Uniswap 높음 core 운영 낮음 brand·standard 장점, UI/API는 별도 낮음 병행 협의
gauge/emission MetaDEX 조건부 높음 매우 높음 token budget·voter network 필요 복잡 초기 제외

v2는 x*y=k full-range pool과 단일 30bp fee로 단순하다. 반면 v3는 특정 range에 capital을 집중하고 여러 fee tier를 쓸 수 있다. 초기 GIWA처럼 유동성이 부족할 때 라우터가 선택할 가격을 만들기에는 후자가 낫다. 다만 range를 벗어나면 fee를 못 벌고, LP가 관리·재조정· gas와 predictable loss를 부담하므로 “효율이 높다”와 “LP가 돈을 번다”는 같은 말이 아니다. (src_221, src_223~src_224, src_230~src_231; clm_309, clm_310, clm_312)

4.2 최소 core

권고 production hypothesis는 다음뿐이다.

  1. immutable, non-upgradeable factory와 pools
  2. 처음에는 correlated pair와 volatile pair에 필요한 fee tier만 허용
  3. user가 직접 소유하는 LP NFT·position; team custody 없음
  4. router는 quote, minimum received와 slippage bound를 명시
  5. verified token registry는 표시 계층이고 permissionless contract를 잠그지 않음
  6. source verification, bytecode hash, deployer·owner·fee recipient 공개
  7. protocol fee switch off; 켤 수 있다면 권한·cap·timelock과 법적 gate를 별도 공시

초기 제외 항목은 managed vault, auto-rebalancer, keeper, farm, gauge, ve-token, bridge, gasless relay, referral, limit order, leverage와 token launch다. 각 기능은 custody·admin· routing·audit surface를 늘린다. (src_211, src_224, src_231, src_234, src_243; clm_311)

4.3 오픈소스와 브랜드

Uniswap v2 core는 GPL-3.0이다. v3 core의 license file은 2023-04-01 이전을 change date로 두고 GPL-2.0-or-later로 전환한다. 이것은 독립 fork 검토 가능성을 열지만, 실제 사용할 core·periphery·SDK·frontend의 파일별 license 의무와 수정 공개 범위는 다시 점검해야 한다. 또 code permission은 Uniswap 이름·로고, canonical status, 기존 audit와 liquidity를 넘겨주지 않는다. 독립 브랜드와 새 감사가 기본이다. (src_222, src_225, src_246; clm_308)

4.4 완전 탈중앙화라는 표현을 피한다

정확한 문구는 “non-custodial, permissionless AMM contracts with an open-source interface”에 가깝다. GIWA의 sequencer·dispute-game 구성과 우리 hosted UI, indexer, token list는 별도 trust layer다. 권한을 공개하고 줄이는 것은 가능하지만 전체 시스템에 단일 운영 표면이 없다고 주장할 수는 없다. (src_204, src_206, src_243; clm_332)

5. fee waterfall과 한국 법률 경계

5.1 같은 ‘수수료’가 아니다

fee 누가 지불 기본 수취인 우리 매출 가능성 초기 상태
Network gas transaction sender GIWA chain fee vault chain과 별도 계약 없이는 없음 필수 비용
LP swap fee trader active LP team이 자기자본 LP면 지분만큼 법률의견 전 Amber
Protocol fee LP fee 일부 또는 pool rule protocol treasury 직접 거래비례 매출 Off / Red
Interface fee 우리 UI 사용자 interface operator 자체 UI flow에 한함 Off / Red
Router/referral fee routed user router/referrer routed output의 일부 Off / Red
Fixed B2B service project customer 개발·보안·데이터 법인 거래와 무관한 정액 상대적 우선

(src_207, src_221, src_226, src_247; clm_317, clm_318, clm_325)

5.2 단순 fee 산식

team LP gross fee
= organic pool volume × pool LP fee × team share of active liquidity

protocol revenue
= organic pool volume × effective protocol take rate

interface revenue
= volume actually routed through our interface × disclosed interface rate

net contribution
= all team receipts
 - incentives - rebates - RPC/indexer - audit/security - compliance/tax
 - LP predictable loss/rebalancing/hedging cost

월 organic volume이 $10m, pool fee가 30bp, team이 active liquidity의 20%를 실제로 차지한다는 산술 예시라면 LP gross fee는 $6,000이다. protocol take가 5bp이면 $5,000, own-interface fee가 10bp이면 $10,000이다. 그러나 후자의 두 항목은 한국 법률상 출시 권고가 아니라 위험 규모를 보여주는 계산이며, LP $6,000도 자산 손실·range 이탈·hedging·gas 전 금액이다. 월 고정비 $10,000을 5bp take만으로 충당하려면 $20m organic volume이 필요하다. gross chain volume을 우리 매출로 세면 안 된다. (src_221, src_226, src_230~src_231; clm_310, clm_317)

5.3 한국 기능별 보수적 등급

Green도 면제나 적법 확정이 아니라 상대적으로 낮은 VASP 노출을 뜻한다.

구조 등급 이유 반드시 꺼둘 것
source code 공개, 미배포 🟢 순수 기술 제공에 가까움 official UI·router·fee wallet
immutable AMM, 운영권 없음 🟠 국내 DEX 전용 safe harbor·직접 판례 없음 proxy·admin·fee setter
team own-capital LP 🟠 own-account 원칙은 유리하나 AMM 직접 판례 아님 외부자금·정산·수익보장
deployer/admin 권한 유지 🔴 지속적 통제의 강한 증거 upgrade·pause·whitelist·sweep
protocol fee switch 🔴 거래비례 이익과 설정권 결합 fee recipient·rate 변경
frontend/interface fee 🔴 이용자 편익을 위한 반복 routing과 대가 fee injection·gasless relay
paid router/aggregator 🔴 경로 선택·실행 지원과 보수 결합 spread·MEV share·order relay
customer LP-token vault 🔴 보관·관리·투자상품 위험 admin withdrawal·guaranteed APR
team transfer tax 🔴 통제·광고·증권성·부정거래 위험 중첩 dynamic tax·exempt list·swapback
fixed B2B dev/security/data 🟢~🟠 거래·보관과 분리할수록 경계 선명 volume·성공보수 연동

대한민국 법은 매매·교환뿐 아니라 그 중개·알선·대행을 영업으로 하는 자를 VASP에 포함한다. 특정금융정보법 제7조상 신고 대상이면 신고가 수리되기 전 영업해서는 안 된다. 대법원은 오로지 자기 계산·자기 이익을 위한 일반 이용자의 반복 거래와 불특정 다수의 편익을 위해 거래하고 대가를 받는 반복 행위를 구분했다. own-capital LP는 상대적으로 유리하지만, team이 DEX·UI·admin·fee를 함께 운영하면 단순 LP라는 설명이 약해진다. (src_234~src_237, src_244; clm_319, clm_320)

금융위의 단순 P2P·wallet platform 반례와 FATF의 underlying-software 구분 때문에 “모든 코드 개발자는 VASP”도 정확하지 않다. 동시에 open source·immutable·non-custodial이라는 label만으로 자동 면제되지도 않는다. 실제 actor, admin key, UI, calldata·route 생성, fee recipient, 고객 편익과 반복 영업을 기능별로 본다. FATF는 한국의 구속법이 아니라 기능 분석의 보조 근거다. (src_234~src_235, src_238, src_243; clm_321)

5.4 권고 수익 순서

  1. 프로젝트에 코드 통합·보안 검토·pool telemetry를 제공하고 원화/법정화폐 정액을 받는다.
  2. team wallet과 자본·LP range·철수 규칙을 공개하고, 서면 의견 뒤 자기자본 LP fee를 검토한다.
  3. protocol·interface·router fee가 꼭 필요하면 actor/flow map을 만든 뒤 전문 변호사의 VASP 의견, 필요한 신고 수리 또는 실질 역할이 분리된 신고사업자 구조를 먼저 완성한다.
  4. protocol fee와 interface fee를 동시에 겹치지 않는다.
  5. fee-share token, transfer tax, hidden spread, referral과 customer asset vault는 초기부터 제외한다.

(src_221, src_226, src_231, src_234~src_244; clm_322~clm_325)

6. organic volume을 만드는 방법

6.1 volume의 다섯 원천

  1. Anchor corridor: redeemability와 bridge path가 검증된 stablecoin과 WETH 교환.
  2. Utility conversion: game, payment, consumer reward를 stable asset으로 바꾸는 반복 수요.
  3. Launch inventory: partner project의 token launch와 treasury liquidity.
  4. Embedded distribution: GIWA Wallet, project UI와 외부 wallet에서 바로 호출되는 route.
  5. Arbitrage/reference market: 외부 시장·bridge가 있어 price discrepancy를 닫는 flow.

첫 번째와 다섯 번째는 production bridge와 canonical asset이 없으면 작동하지 않는다. 두 번째와 세 번째는 project가 실제 token·contract·user route를 서면으로 제공해야 한다. 네 번째는 좋은 가격과 integration acceptance가 필요하다. logo partnership만으로 생기는 volume source는 없다. (src_203, src_208, src_215~src_217, src_221, src_227; clm_303, clm_314, clm_315)

6.2 체결 품질을 먼저 산다

인센티브를 쓴다면 raw TVL·volume이 아니라 다음에만 제한한다.

  • time-weighted in-range depth
  • target order size의 quote improvement
  • liquidity uptime와 public lock/withdrawal terms
  • independent LP의 own-capital commitment
  • finite, declining budget와 명확한 종료일

보상 조건에서 volume, 거래 횟수, 가격목표를 빼야 한다. reward가 왕복 수수료보다 크면 self-trade를 경제적으로 유도한다. Aerodrome의 gauge flywheel은 깊은 시장을 조직하는 한 방법이지만 새 token, voter network와 지속 emission budget이 필요하다. 독립 분석에서도 보상 기간에 늘어난 liquidity가 종료 후 감소했고 지속 효과는 모든 pool에서 확인되지 않았다. 그대로 복제할 이유가 없다. (src_228~src_233, src_239~src_240; clm_313, clm_324)

6.3 raw volume을 버린 KPI

organic dataset에서 먼저 제외할 것:

  • team·treasury·known LP와 related wallets
  • faucet·mock asset transactions
  • same-fund round trip과 sybil cluster
  • reward eligibility만 노린 swaps
  • team UI가 자기 pool에 보낸 internal test
  • reverted transaction과 duplicated indexer events

그 뒤 다음을 측정한다.

KPI 질문
P50/P90 price impact 의도한 크기의 주문을 얼마나 잘 받는가
external funded wallets 관계 없는 경제 주체가 들어오는가
7d/30d repeat rate 한 번 찍고 떠난 traffic인가
partner/router share 우리 marketing 밖에서도 route가 오는가
organic volume / real TVL 자본이 실제로 회전하는가
fees / incentive cost 주문 흐름을 사는 비용보다 가치가 큰가
post-incentive retained depth subsidy가 끝나도 liquidity가 남는가
top-10 share 극소수 지갑이 숫자를 만드는가
swap success and stale quote UX가 아니라 execution이 안정적인가

peer-reviewed research는 DEX의 비정상 거래를 pattern·entity method로 분류할 수 있음을 보였지만 그 수치는 법원 확정이 아니다. 따라서 자동 플래그 뒤 수동 검토와 공개 exclusion rule을 함께 둔다. (src_229, src_232~src_233, src_239~src_240; clm_316)

각 미팅에서 받아야 하는 것은 logo가 아니라 다음 여섯 가지다.

  1. production token contract와 legal issuer
  2. 실제 유입 화면과 router 호출 지점
  3. 월간 intended swap users와 trade-size distribution의 근거
  4. 양쪽 자산의 own-capital liquidity commitment
  5. incentive budget, 종료일과 related-wallet list
  6. contract·analytics·security contact와 incident owner

7.2 pair를 적게 연다

첫 공식 corridor는 WETH / canonical stablecoin 하나다. project token은 stable quote에 연결하고, project-to-project 또는 meme-to-meme pair는 초기 공식 화면에서 만들지 않는다. 같은 pair에 여러 fee tier를 동시에 열어 scarce liquidity를 갈라놓지도 않는다. permissionless contract에서 임의 pool 생성을 막을 필요는 없지만, 공식 token list와 route에는 검증된 pool만 기본 표시한다. (src_204, src_215, src_221, src_227; clm_327)

Mock USDC, oracle의 USDC price feed, 이름만 USDC인 ERC-20은 redeemable settlement asset이 아니다. issuer address, mint/burn authority, L1 backing, bridge canonicality와 pause· freeze 권한을 확인한 뒤에만 기준자산으로 쓴다.

8. 90일 validation scorecard

이 숫자들은 역사적 사실이나 수익 예측이 아니라 현재 실데이터가 없는 상태에서 founder가 채택·수정할 내부 go/no-go threshold다. mainnet 전에는 testnet rehearsal에만 적용하고 매출·TVL로 표현하지 않는다.

8.1 출시 전 hard gates

다음이 모두 충족돼야 한다.

  • official public mainnet RPC, chain ID, explorer와 bridge contracts
  • issuer 또는 canonical bridge가 명확한 stable quote asset 하나
  • 서로 독립적인 production RPC 두 경로와 indexer
  • core·periphery·frontend audit, source verification와 incident plan
  • written integrations 두 건: launch inventory 하나 + wallet/consumer surface 하나
  • intended order size의 P90 all-in price impact ≤1%
  • aggregator/analytics onboarding package 제출 가능 상태
  • actor/admin/data/asset/fee flow map과 한국 전문 변호사 서면 의견

초기 intended order size를 $10k equivalent로 가정할 수 있으나 실제 partner order distribution을 받으면 다시 정해야 한다. (src_201, src_203~src_204, src_215, src_217, src_219, src_231, src_234, src_244; clm_328)

8.2 첫 90일 내부 checkpoint

시점 provisional checkpoint 실패 시
Day 30 external funded wallets ≥100, 7d repeat ≥20%, partner-surface share ≥20% pair·distribution 재설계
Day 60 external funded wallets ≥500/month, non-incentivized volume ≥40%, top-10 share <50%, external routes ≥30% 확장 중지
Day 90 trailing-30d organic volume ≥ average real TVL의 5배, non-incentivized ≥50%, team receipts가 variable ops+incentives의 ≥25% 종료 또는 integration-only pivot

이 checkpoint는 “많이 거래하라”는 사용자 보상이 아니다. 내부 관찰 기준이며 reward는 거래량에 연동하지 않는다.

8.3 kill criteria

다음 중 하나면 real-money launch 또는 확장을 중단한다.

  • public mainnet 또는 canonical stablecoin이 없음
  • only manual RPC와 7-day bridge뿐이고 LP rebalancing route가 없음
  • partner가 contract·route·capital 없이 logo만 제공
  • Day 30 external funded wallets &lt;100 또는 organic daily average &lt;$50k
  • Day 60 non-incentivized share &lt;30%, top-10 share >70% 또는 suspected self/wash >20%
  • Day 60까지 third-party wallet/router/indexer inflow가 0
  • Day 90 team receipt가 variable cost·incentive의 25%도 못 덮음
  • subsidy 제거 뒤 volume이 70% 이상 사라짐
  • canonical asset depeg, bridge pause, unresolved critical audit issue 또는 swap failure >1%

이 기준은 gross TVL 하나가 아니라 organic flow, concentration, execution, LP risk와 legal readiness를 묶는다. (src_229~src_233, src_239; clm_329)

9. 최소 UI/UX와 신뢰 표면

9.1 필요한 화면

Swap

  • connect wallet / add correct chain
  • verified token name, symbol, address와 warning
  • exact-in 또는 exact-out quote
  • route, pool, fee tier와 quote timestamp
  • network gas / LP / protocol / interface fee를 별도 표시
  • price impact, slippage, minimum received와 deadline
  • approve와 swap 상태, explorer link

Liquidity

  • pair와 current price
  • user-owned range와 out-of-range warning
  • fee tier, deposited assets와 earned fees
  • add, collect, remove
  • no APR promise; historical fee와 risk를 분리

Pool facts

  • contract, factory, router와 bytecode/source status
  • reserve 또는 active liquidity, 24h fee와 volume methodology
  • deployer, owner, admin, pauser, fee recipient
  • audit, bug bounty, incident contact와 last updated time

초기에는 chart, leaderboard, farm, referral, bridge, limit order, cross-chain, NFT badge와 meme feed를 넣지 않는다. Simple은 정보를 숨기는 것이 아니라 거래 결정에 꼭 필요한 정보만 정확히 보여주는 것이다. (src_203, src_217, src_220~src_221, src_226~src_227; clm_331)

9.2 오픈소스 운영 원칙

  • core, periphery, interface와 indexer repository 분리
  • reproducible build와 deployed bytecode hash
  • no proxy, hidden admin, upgrade or rescue path
  • public fee-recipient wallet과 change log
  • signed release tag, dependency lock와 vulnerability disclosure
  • community mirror가 가능하도록 read-only API schema 공개

오픈소스는 보안·법률의 대체물이 아니다. 그러나 동일 bytecode, 권한과 fee를 누구나 검증하게 만들면 partnership과 routing review의 비용을 줄일 수 있다. (src_225~src_227, src_234~src_235, src_243, src_246; clm_308, clm_321)

10. Uniswap이 오거나 오지 않을 때

10.1 현재 답

Uniswap의 official v3 deployment registry와 Trading API support table에는 GIWA가 없다. Uniswap의 general strategy는 새 asset과 chain으로 확장하고 liquidity bootstrapping에 투자한다는 방향을 제시하지만, GIWA proposal·grant·integration·launch date를 뜻하지 않는다. (src_201, src_218~src_220, src_245; clm_306, clm_333)

10.2 병행할 proposal package

canonical 협의를 시작할 때는 다음을 준비한다.

  1. official mainnet chain facts와 security architecture
  2. canonical bridge·stablecoin and WETH addresses
  3. deterministic v2/v3 deployment addresses와 verification
  4. audit, bug bounty, monitoring와 emergency communication
  5. committed LP capital and anchor issuers
  6. GIWA Wallet and ecosystem distribution commitments

canonical status만 받은 뒤 Labs UI와 liquidity가 자동으로 온다고 가정해서는 안 된다. (src_218~src_220, src_227; clm_307)

11. 최종 제안

11.1 제품 정의

GIWA-native minimal liquidity venue: verified anchor assets와 소수 partner pool에 concentrated liquidity를 모으고, 가장 단순한 trader UI와 가장 투명한 fee·admin·contract facts를 제공하는 open-source non-custodial DEX.

이것은 “또 하나의 generic swap”이 아니다. 성패는 core code보다 canonical quote, wallet distribution, anchor partners와 independent liquidity commitment를 선점하는 데 달렸다.

11.2 무엇을 하지 않는가

  • DEX token·ve-token·farm·perpetual emissions
  • team transfer tax, buy/sell tax와 hidden spread
  • volume mining, wash trading, price support와 listing promise
  • customer LP-token custody와 managed vault
  • mainnet·USDC·Uniswap·GIWA Wallet 지원을 근거 없이 가정
  • testnet volume·TVL을 실수요로 홍보

가상자산이용자보호법상 통정·가장매매, 인위적 가격·거래량 형성과 허위·중요사항 누락은 금지선이다. fee-share·buyback을 tokenholder return으로 약속하면 투자계약증권 검토도 추가된다. GIWA가 별도 native token을 계획하지 않는 만큼 초기 DEX token은 필요도 없다. (src_205, src_239~src_242; clm_323, clm_324)

11.3 다음 결정

지금 내려야 할 결정은 contract를 쓰는 결정이 아니라 다음 세 문서를 확보하는 결정이다.

  1. GIWA distribution term sheet: wallet, canonical assets, launch timing과 project routing
  2. Liquidity commitment sheet: 자본 소유자, pair, range, 기간, withdrawal와 disclosure
  3. Korean actor-and-fee legal memo: core, UI, router, admin, LP와 각 recipient의 역할

세 문서가 없으면 멋진 DEX가 아니라 유동성 없는 fork와 법적 책임만 갖게 된다. 세 문서가 나오면 UI는 정말 단순해도 된다. 그때 우리가 팔아야 할 것은 화면이 아니라 좋은 체결과 신뢰할 수 있는 시장이다. (src_208, src_215~src_220, src_234~src_244; clm_303, clm_314, clm_319, clm_328)
