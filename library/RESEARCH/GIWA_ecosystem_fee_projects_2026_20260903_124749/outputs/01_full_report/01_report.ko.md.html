기준일: 2026-09-03 KST 연구 모드: Insane Research strict 경계: research_only=true, strategy_consumption_allowed=false, order_input=false

이 문서는 기술·사업·규제 리서치이며 법률·세무·투자 자문이 아니다. “상대적 저위험”은 적법 확인이나 인허가 면제를 뜻하지 않는다. 본 조사에서는 배포, 서명, 거래, 유동성 공급, faucet claim, 토큰 발행·판매를 하지 않았다.

1. 판단 요약

1.1 한 문장 결론

또 하나의 스왑·밈코인 발사대를 서두르기보다, GIWA를 첫 adapter로 삼는 chain-agnostic Pool Passport / Liquidity Launch OS를 만들어 token·pool의 권한·fee· 코드·유동성 상태를 표준 공시하고 고정 B2B fee를 받는 것이 현재 가장 좋은 위치다.

그 이유는 세 가지다.

  1. GIWA는 아직 공개 메인넷이 아니라 Sepolia 단계다. 공식 문서와 현재 node 저장소는 mainnet과 GIWA Wallet을 개발 중으로 표시한다. 공개 테스트망은 chain ID 91342, ETH gas다. (src_101, src_102, src_104; clm_201)
  2. 스왑 시장은 비어 있지 않다. GIWATER, Joseon.fun, Ammora와 기타 AMM 실험이 있고, 한 V3형 test stack에서는 9월 2일 성공 거래까지 확인됐다. 다만 공식성·감사·실유동성은 별개다. (src_110~src_113, src_117~src_120; clm_208, clm_209, clm_228)
  3. 한국 이용자 거래를 반복 연결하고 건별 fee를 받는 UI/router는 비수탁이라도 VASP 중개·알선·대행으로 평가될 위험이 높다. 반면 거래 기능과 분리된 고정 구독·API·보안 리포트는 상대적 경계가 훨씬 선명하다. (src_130~src_133, src_136; clm_217, clm_218, clm_222)
  4. Uniswap의 일반 확장 전략은 기회지만 GIWA별 공식 준비 신호는 없다. “빗썸 신체인”도 현재 공개 근거로 확인되지 않아, 어느 한 체인의 소문에 종속된 DEX보다 재사용 가능한 검증·유동성 운영 계층이 낫다. (src_121, src_125, src_126, src_145~src_150; clm_229~clm_232)

2. “며칠 전에 발표된 프로젝트”는 무엇이었나

2.1 공식 발표와 자기발표를 구분해야 한다

공식 GASOK 페이지에 따르면 Phase 3는 2026년 8~9월의 MARKET READINESS & LAUNCH 단계다. 목표는 테스트넷 유저 지표와 프라이빗 메인넷 배포이고, KBW Demo Day는 10월이다. 페이지는 5개 중복 가능 트랙, 트랙별 최대 3팀을 명시한다. 또 GASOK 선발·지원은 Upbit의 디지털 자산 거래지원과 무관하다고 못 박는다. (src_104; clm_204, clm_206)

8월 24일~9월 2일에 실제로 보인 것은 하나의 공식 roster 게시가 아니라 각 프로젝트가 이메일 수신 또는 Phase 3 합류를 알리는 rolling self-announcement였다. Layergg도 8월 25일 “현재까지 확인된” 아홉 곳을 열거하고 추가 프로젝트의 댓글을 요청했다. 커뮤니티 GIWA.eco는 그 뒤 공개 글을 모아 43개 프로젝트 중 29개를 selected로 표시하면서 스스로 “GIWA 공식 선정 명단은 공개된 적이 없다”고 경고한다. (src_114~src_116; clm_204, clm_205)

따라서 현재 정확한 표현은 다음과 같다.

  • 허용: “29개 프로젝트가 공개 자기발표·프로필·제3자 자료에서 Phase 3 합류를 주장했다.”
  • 금지: “GIWA가 29개 최종 선정팀을 공식 발표했다.”
  • 금지: “Phase 3 합류는 mainnet launch, grant 수령, Demo Day 완료 또는 Upbit 상장 후보임을 뜻한다.”

공식 트랙 cap과 커뮤니티의 29개 표기는 설명되지 않은 긴장이 있다. 규칙 변경, 중복 팀, 복수 프로젝트, 상태 오분류 등 여러 가능성이 있으므로 GIWA의 이름별 공식 roster가 나오기 전까지 공식 확정 숫자를 만들지 않는다. (src_104, src_114; clm_206)

3.3 “빗썸도 체인을 준비한다”는 주장

2026-09-03 현재 이 주장을 뒷받침하는 빗썸코리아의 체인명, chain ID, node 또는 rollup repository, 개발 문서, testnet·mainnet 일정은 찾지 못했다. 검증된 공식 GitHub 조직에는 bithumb-ai-trade-kit 한 개의 공개 repository만 보였고, 현재 채용면에는 blockchain backend, wallet security, non-custodial wallet 역할이 있으나 이것만으로 L1/L2 개발을 추론할 수 없다. 현재 사업 페이지도 거래소를 설명한다. (src_147~src_149; clm_231)

검색되는 Bithumb Chain은 2019년 Bithumb Global이 발표한 별도 역사적 계획이다. 이 명칭을 2026년 빗썸코리아의 신규 체인 증거로 재활용하면 법인·시점·프로젝트를 혼동한다. (src_150; clm_231)

따라서 Bithumb-chain adapter는 코드가 아니라 watchlist 요구사항으로만 둔다. 공식 문서·RPC·chain ID·genesis·bridge·explorer가 공개되면 새 adapter를 추가하고, 그 전에는 예산·토큰·유동성을 배정하지 않는다. 제보 원문이 생기면 이 판정을 다시 열어야 한다.

4.2 버전별 선택

버전 기술·라이선스 GIWA에서의 판단
v2 단순 constant-product, GPL 계열 만들기 쉽지만 자본효율·포크 난립·차별성 약함
v3 concentrated liquidity; core change date 경과, GPL-2.0+ 독립 testnet 연구의 현실적 기준선; canonical·상표·감사 별도
v4 singleton·hooks·dynamic fee R&D 매력은 높지만 주요 core BUSL production 제한 때문에 HOLD

v3 코드를 쓸 수 있다는 것과 공식 Uniswap을 운영한다는 것은 전혀 다르다. canonical v2/v3는 UAC/DAO 절차가 있고, app.uniswap.org 지원은 별도 Labs 결정이다. 소프트웨어 license도 Uniswap 상표권을 주지 않는다. 독립 브랜드와 명확한 attribution이 필요하다. (src_122, src_123, src_139; clm_211, clm_212)

v4 주요 core는 BUSL-1.1이고 공식 지원 문서는 2027-06-15 전 commercial/production use가 제한된다고 설명한다. Additional Use Grant 또는 별도 license를 확인하지 않은 production fork는 제안에서 제외한다. (src_124, src_141; clm_213)

4.3 Uniswap이 GIWA를 준비할까

현재 답은 “기술적으로 제안할 수 있으나, 준비 중이라는 공식 근거는 없다”다. 공식 v3 배포 목록, developer deployment table, Trading API 지원표와 최신 governance 표면에서 GIWA·91342 또는 GIWA 배포 제안을 찾지 못했다. 다른 네트워크의 공개 RFC가 governance에 등장하는 것과도 대조된다. (src_121, src_125, src_126, src_145; clm_229)

Uniswap의 UNIfication 전략은 “새 자산이 존재하는 곳”에 protocol을 배포하고 liquidity bootstrapping 도구와 launcher에 투자하겠다고 밝힌다. 따라서 GIWA public mainnet, canonical asset, 감사된 초기 liquidity와 실제 사용 수요가 나온 뒤 GIWA 또는 ecosystem 팀이 v3 canonical proposal을 제시할 전략적 여지는 있다. 하지만 이는 일반 방향성이지 GIWA와의 협상, engineering 일정, grant 또는 app 지원 약속이 아니다. (src_101, src_122, src_145, src_146; clm_230)

준비 순서는 다음과 같다.

  1. 지금: GIWA Sepolia에 대한 독립 adapter, pool passport, fee·권한 monitor를 구축한다.
  2. 공식 public mainnet·asset·bridge 이후: 감사된 배포자, deployer address, salt, bytecode, liquidity commitment를 포함한 canonical v3 제안서를 준비한다.
  3. DAO/UAC 승인과 별개로: Labs app·API 채택을 따로 협의한다.
  4. 승인 전: 독립 V3형 제품을 Uniswap on GIWA라고 표시하거나 상표·공식성을 암시하지 않는다.

4.4 우리가 Uniswap으로 돈을 벌 수 있는 경우

  1. canonical v3 유치 + 별도 UI: protocol fee는 우리 것이 아니다. 통합·운영·B2B SaaS 또는 법적으로 허용된 interface fee가 수익원이다.
  2. 독립 v3-derived AMM: fee controller를 설계할 수 있지만 official Uniswap이 아니며 liquidity, routing, indexer, audit, governance와 규제 부담을 모두 우리가 진다.
  3. LP 참여: 우리 treasury가 실제 liquidity를 제공하면 LP fee를 얻을 수 있지만 impermanent loss, range, exploit, price·market-abuse 위험을 감수한다.
  4. v4 hooks: dynamic fee와 custom accounting은 매력적이나 지금은 license와 새로운 공격면 때문에 testnet research까지만 한다.

(src_122~src_127, src_139, src_141, src_142; clm_211~clm_215)

5. fee는 누구에게 가는가

5.1 fee waterfall

사용자 총비용
├─ network gas ───────────────> GIWA/OP Stack configured fee-vault recipients
├─ pool LP fee ───────────────> active liquidity providers
├─ protocol fee (있을 때) ───> 해당 protocol governance/treasury
├─ interface/router fee ──────> UI/integrator가 명시한 recipient
└─ service fee ───────────────> 공시·검증·API·운영 서비스를 제공한 회사

GIWA 문서는 execution fee와 security fee를 설명하고, OP Stack은 base, sequencer, L1, operator fee를 각 vault에 모아 configured recipient로 보낸다. dapp이 transaction을 발생시켰다는 이유만으로 gas share를 받지 않는다. (src_106, src_128, src_129; clm_214)

Uniswap도 interface, protocol, LP fee를 분리한다. canonical deployment의 app 운영자라는 이유만으로 protocol fee를 소유하지 않는다. 네트워크 비용과 우리가 설계한 서비스 요금도 완전히 분리해 표시해야 한다. (src_127, src_142; clm_215)

5.2 현실적인 매출식

월매출 = B2B 구독 + API 사용료 + 고정 검증/모니터링 리포트 + 공개된 sponsor fee
       + 조건부 LP fee + 법적으로 허용된 interface fee

순매출 = 월매출 - RPC/indexer - 보안감사 - 법무/AML - 보험 - 고객지원
       - incentive/subsidy - LP 손익

테스트넷 tx, mock-token nominal TVL, wallet address count를 매출 추정에 넣지 않는다. GASOK grant도 runway일 뿐 recurring fee가 아니다. GIWA 테스트넷 토큰을 이용한 유상 거래·무승인 상업 홍보에는 약관 제한이 있으므로 testnet fee switch는 끈 채 로컬 회계 시뮬레이션만 한다. (src_104, src_107; clm_203)

5.3 초기 유동성과 “거래세” 설계

여기서 거래세라는 표현은 정부가 걷는 세금으로 오해될 수 있다. 제품에서는 반드시 LP fee, protocol fee, interface fee, service fee 중 실제 항목과 recipient를 체결 전에 표시한다. ERC-20 transfer tax는 0으로 고정한다. 숨은 매수·매도 차등세, 운영자가 올릴 수 있는 세율, sell tax, fee-on-transfer 토큰은 routing·회계·신뢰를 깨뜨리고 시장질서·부정표시 위험까지 더한다. (src_134, src_144; clm_221, clm_233, clm_234)

현재부터 가능한 fee ladder는 다음과 같다.

순서 수익원 현재 설정 수취 조건
1 고정 service fee ON 후보 거래와 무관한 원화 구독·API·검증 리포트
2 own-account LP fee OFF / Amber 팀 자체자본만, 서면 법률의견·시장통제·손실한도 이후
3 interface/router fee OFF / Red 한국 대상이면 기능별 VASP 판단·필요 신고·파트너 구조 이후
4 자체 AMM protocol fee OFF / Red 감사·governance·법률·유동성·공시 gate 이후
5 token transfer tax 0 / 금지 숨은 세금·buyback·보유자 수익분배 금지

canonical Uniswap의 LP fee는 실제 active LP에게, governance-enabled protocol fee는 Uniswap 쪽 메커니즘에 귀속한다. 우리가 자본을 직접 공급한 비율의 LP fee 또는 별도로 제공한 서비스의 명시적 fee만 우리 매출로 잡는다. (src_122, src_127, src_142, src_146; clm_215, clm_234)

초기 유동성은 다음 순서로 만든다.

  1. 자산 gate: issuer-backed quote asset, canonical bridge/address와 redeemability가 확인되기 전에는 mock USD pool을 열지 않는다.
  2. commitment registry: creator·treasury·독립 LP가 넣을 실제 자기자본, lock 기간, wallet, fee tier, 최대 손실·철회 조건을 먼저 공개한다. 고객 자금은 받지 않는다.
  3. 가격발견: 선착순·내부자 우선 curve보다 공개 batch auction/LBP의 시뮬레이션을 준비하되, 실제 모집·배분·체결은 신고 VASP 또는 적법한 파트너가 담당한다.
  4. POL: 팀이 승인한 자기자본만 protocol-owned liquidity로 넣고, LP NFT와 회수권을 multisig·timelock·공개 lock에 둔다. 가격 방어를 약속하지 않는다.
  5. 인센티브: raw volume이 아니라 time-weighted two-sided depth, uptime, spread, 7·30일 잔존 유동성을 보상한다. 관계자·self-route·순환 주소는 지표와 보상에서 뺀다.
  6. 확장: 체인별 재고와 pool 회계는 분리한다. canonical bridge와 issuer 승인 전에는 같은 ticker를 임의 bridge해 “동일 자산”으로 취급하지 않는다.

이렇게 하면 “첫날 거래량”을 사는 것이 아니라 회수되지 않는 깊이와 실제 사용을 산다. 거래량 mining·wash rebate·가격·상장 보장은 금지한다. (src_134, src_140, src_144, src_146; clm_216, clm_219, clm_221, clm_233)

6. 대한민국 법률·규제 경계

6.1 VASP

가상자산이용자보호법 제2조의 VASP 범위에는 매매, 교환, 일정 이전, 보관·관리뿐 아니라 매매·교환의 중개·알선·대행 영업이 들어간다. 특정금융정보법 제7조는 운영 예정자를 포함해 FIU 신고를 요구하고, 2026-08-20부터 대주주, 재무·사회적 신용, 조직·인력·전산설비· 내부통제 심사가 강화됐다. (src_130, src_131, src_136; clm_217)

대법원 2024도10710은 순수 자기 계산의 일반 이용자와, 불특정 다수의 편익을 위해 대가를 받고 반복 거래하는 영업을 구분했다. 따라서 사용자 지갑을 보관하지 않는다는 사실만으로 swap UI·router의 건별 fee가 안전해지지 않는다. calldata·quote·route·relayer·admin· fee recipient와 실제 운영을 전부 보고 판단해야 한다. (src_132, src_133; clm_218)

6.2 토큰과 시장질서

“밈” 또는 “utility”라는 이름은 증권성을 제거하지 않는다. 공동사업에 돈을 넣고 주로 팀의 노력 결과에 따라 손익을 받는 권리가 있다면 투자계약증권 문제가 생길 수 있다. 특히 fee share, revenue share, buyback·소각을 수익 환원으로 홍보하는 구조는 고위험이다. (src_135, src_137, src_138; clm_220)

미공개정보 이용, wash/matched trading, 인위적 거래량·가격 형성, 거짓·중요사항 누락은 가상자산이용자보호법의 금지선이다. 팀 지갑 순환거래, “Upbit 상장 확정”, 가격 보장, 숨은 mint·freeze·proxy·LP 회수권을 배제한다. (src_134, src_144; clm_221)

7. 제안 프로젝트와 우선순위

7.1 1순위 — Pool Passport / Builder Trust Suite

사용자가 보는 것

각 token·pool에 하나의 passport를 제공한다.

  • 배포 chain, address, bytecode hash, source verified/full verified 구분
  • proxy와 implementation, owner/admin, multisig quorum, timelock
  • mint, freeze, blacklist, transfer-tax, anti-sell, pause, upgrade 권한
  • LP token/NFT 소유자, lock·unlock·withdraw 권한, 집중유동성 range
  • protocol/LP/interface fee와 각 recipient
  • treasury·team·vesting 주소의 공시된 분류와 변경 이력
  • Dojang schema, attester, timestamp의 원문 표시
  • explorer transaction과 project self-claim을 서로 다른 evidence badge로 표시

절대 표시하지 않는 것

  • “안전 보장”, “러그 불가”, “공식 GIWA”, “Upbit 검증·상장 후보”
  • 주소 수를 사용자 수로, testnet tx를 채택으로, mock value를 TVL로 바꾼 숫자
  • 돈을 낸 프로젝트를 알고리즘 상단에 올리면서 sponsor 표시를 숨기는 것

수익 구조

고객 제품 fee
Builder continuous contract/pool monitoring 월 정액
Wallet·directory risk/disclosure API 고정 tier + request allowance
Fund·partner due-diligence snapshot 고정 report fee
Ecosystem sponsor 공개된 research sponsorship 월 정액, ranking과 분리
Enterprise private alert webhook·SLA 월/연 계약

거래량, TVL, token sale, listing 성공과 요금을 연결하지 않는다. 팀은 사용자의 order, route, signature, asset을 취급하지 않는다. 이것이 fee를 포기하는 것이 아니라 fee의 법적 원인을 거래 중개에서 데이터·보안 서비스로 바꾸는 것이다. (src_108, src_143, src_130~src_133; clm_222, clm_224, clm_225)

7.2 밈 레이어 — Dokkaebi Tile 문화 배지

금융 밈코인 대신 Pool Passport에 연결되는 양도 불가 culture/build credential을 쓴다. 예: 위험 공시를 완성한 builder에게 “투명 기와”, bug report 기여자에게 “도깨비 수리공” badge를 발급한다.

  • secondary market, 현금환급, 수익배분, 상장 약속 없음
  • badge 보유가 투자 우선권·토큰 allocation을 주지 않음
  • 수익은 sponsor, merch, community membership 또는 B2B suite에서 발생
  • IP, 표시광고, 개인정보, 환불·전자지급 적용은 별도 검토

이는 상대적으로 위험을 낮추는 설계이지 “NFT라서 합법”이라는 결론이 아니다. (src_130, src_135, src_137; clm_223)

7.3 확장 모듈 — chain-agnostic Liquidity Launch OS

GIWA를 첫 adapter로 만들되 데이터 모델은 chain에 종속시키지 않는다.

Chain Watcher
  └─ official chain/RPC/explorer/asset evidence
      └─ Pool Passport
          └─ issuer/admin/fee/LP-rights disclosure
              └─ Liquidity Commitment Registry
                  └─ partner-operated launch adapter (disabled by default)
                      └─ depth/retention/fee accounting

Bithumb adapter 같은 이름은 공식 체인이 검증될 때만 활성화한다. 그 전에도 chain watcher, schema, simulation, fee ledger는 재사용할 수 있다. 실제 order·auction·router·LP custody는 초기 OS가 수행하지 않고 신고·허가와 기능상 역할을 갖춘 파트너 adapter 뒤로 둔다. 이 구조는 체인 소문이 틀려도 제품·고객·코드를 버리지 않게 한다. (src_101, src_117, src_118, src_122, src_147~src_150; clm_231, clm_232, clm_234)

9. Confidence, refuted, unresolved

높은 확신

  • 공개 GIWA는 Sepolia 91342이고 mainnet·GIWA Wallet은 공식 자료상 개발 중이다.
  • 9월 2일 V3형 mock stack에 성공 test swap이 있다.
  • official Uniswap deployment/API 목록에 GIWA가 없다.
  • Uniswap이 GIWA를 준비 중이라는 공개 제안·일정·협업 신호는 확인되지 않는다.
  • v3 change date와 v4 BUSL production 제한 문구가 존재한다.
  • network gas, LP, protocol, interface, service fee는 다른 계층이다.
  • 한국 법문은 거래 중개·알선·대행과 FIU 신고를 포함한다.

중간 확신

  • 29개 Phase 3 공개 주장의 각 팀별 mapping. 공개 post가 삭제·수정될 수 있고 official roster로 교차되지 않았다.
  • 현재 프로젝트들의 지속 운영·코드 일치성. 앱·API·explorer의 시점 관찰만 수행했다.
  • 빗썸 신규 체인은 공식 공개 자료에서 확인되지 않았다. 다만 비공개 개발의 부재까지 증명한 것은 아니므로 원문 제보 또는 공식 문서가 나오면 즉시 재검토한다.
  • Pool Passport가 경쟁 공백을 차지할 가능성. 고객 인터뷰와 가격 실험은 아직 없다.

반박된 초기 가정 3건

  • “GIWA에는 스왑이 전무하다” → testnet 거래와 여러 제품으로 반박.
  • “dapp이 chain gas를 자동 수익화한다” → fee-vault 구조로 반박.
  • “공식 native GIWA coin이 예정돼 있다” → 공식 FAQ의 ETH/no-new-token 설명으로 반박.

미확정 4건

  • public mainnet의 실제 공개 시점과 production endpoints
  • 공식 Phase 3 팀명·총수
  • 익명 V3형 stack의 운영 계획·감사·mainnet 지위
  • 구체적 non-custodial UI 구조에 대한 한국 규제기관의 최종 분류
